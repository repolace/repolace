## Branch and PR flow within a task (decided)

Inside the per-task clone:

1. **Clone** at the target branch; this is the base commit.
2. **Index** from the clean tree (before any edits — see above).
3. **Baseline test run** at the base commit, recording the pass/fail set the success criteria compare against.
4. **`git checkout -b`** an agent branch. Plain branch, not a worktree: a worktree exists to share one object store across several trees, which the persistent-cache design needed and this one does not.
5. **Agent works on that branch, committing each edit attempt.** The commits are checkpoints, not history for humans — they let the Debugger `git reset` back to a prior attempt instead of trying to un-edit a bad state, and give the trace UI a per-attempt diff.
6. **Verify** on the branch; loop back to Edit on failure, bounded retries.
7. **Review** the branch against the base: `git diff <base>...<agent-branch>` is exactly what the Reviewer reads and what the PR will show.
8. **Squash** to a single clean commit, so the PR is not "attempt 1, attempt 2, fix debug output".
9. **Push the branch to the remote and open the PR** against the target branch.
10. **Delete the clone.**

**As built in Phase 1 (what differs from the list above, and why).** Steps 5-7 changed shape when the agent became a single tool-loop agent rather than planner/editor/debugger roles. There are two kinds of commit on the agent branch. A *scored attempt* is made by `AttemptScorer.verify_attempt` (`pipeline/repolace_pipeline/attempts.py`): it commits the tree, runs the scored suite, records the `task_test_runs` row. A *checkpoint* is made by the `run_python` and `run_tests` tools before they hand the tree to the sandbox, because the export refuses a tree that differs from HEAD; checkpoints are never scored. So HEAD can be ahead of the last scored attempt, and **`AgentResult.last_attempt` is the only scored state**: before reading the diff, squashing or pushing, the pipeline `rewind_to(last_attempt.commit_sha)` whenever HEAD differs (or to the base commit if nothing was scored). Otherwise the PR would carry edits no suite ever ran against, under a verdict that belongs to an earlier commit. Step 7 is `review_diff()` feeding `tasks.patch_diff` and the PR body; there is no Reviewer agent in Phase 1. Step 3 can also end the task early: an unusable baseline, or a curated fail-to-pass test that was not red at the base commit, completes the task as inadmissible *without running the agent* (an agent run against an unscoreable instance would burn its budget for a result that is thrown away). **The unusable-baseline exit applies to product tasks too**, not only to benchmark instances: `_inadmissible_instance` checks `baseline.error` before it looks for an instance, and pytest's exit code 5 (no tests collected) is not a scoreable exit, so **a product task on a repository with no pytest tests never runs the agent**; it completes after the baseline with no outcome and no PR. That is the benchmark rule applied where it has no headline to protect (product mode has no score to keep honest; its PR gate is `agent_verdict`, which would refuse an unusable baseline anyway). Recorded, not changed: running the agent there would need a gate that means something without a baseline. The exception is a baseline that never reached the container runtime (`SandboxUnavailable`): that is repolace's failure, not the instance's, so the task is `failed` (the baseline row is still recorded). Before this was split out, a dead daemon completed the task as inadmissible, and gold validation drops an instance on exactly that.

**Step 9 is the part that is easy to overlook:** the branch has to exist on GitHub for a PR to reference it, so it must be pushed before the temp directory is discarded. That requires the App installation to hold `contents: write`. Installation tokens expire after an hour and a retry loop can outlive one, so the token must be refreshed immediately before the push rather than minted once at task start and assumed valid.

**Correction to an earlier revision of this note (matters, don't undo it):** it said the clone remote should carry the installation token as `https://x-access-token:<token>@github.com/...`. **Do not do that.** Git writes the remote URL into the checkout's `.git/config`, and step 6 runs LLM-generated code against that same checkout. An agent that reads `.git/config` would be holding a live token with `contents: write` on *every repo the App is installed on* — the blast radius is the whole installation, not this one task.

The token therefore never touches the checkout and never appears in `argv` either. Instead every git invocation carries a per-command credential helper, `git -c credential.helper='!f() { ... }'`, which echoes the token from an environment variable the subprocess is given. `-c` does not persist into the cloned repo's config, so the stored remote stays the plain unauthenticated URL. The preceding `-c credential.helper=` clears any inherited global helper first, so a developer's keychain cannot answer with a different account.

### The part that keeping the token out of the tree does *not* fix

Security review of the implementation found the above is necessary but nowhere near sufficient, and the gap is worth stating plainly because it is easy to feel finished after solving the first half. **The token is not in the checkout, but the checkout still controls where the token is sent and what code the host runs.** `.git` lives inside the tree the sandbox writes to, and git treats parts of `.git` as executable configuration.

Two concrete failures, both demonstrated against this code:

1. **Credential exfiltration.** `push` resolves `origin` from `.git/config`. Verify can rewrite `remote.origin.url`, or add a `url.<evil>.insteadOf` rule (which rewrites *explicit* URLs too, so passing a URL instead of a remote name is not a fix), or set `http.proxy`. A credential helper that answers whatever it is asked then hands the installation token to an arbitrary host over plain HTTP. **Fixed:** the helper now parses git's stdin and releases the token only for `protocol=https` + the expected host, which is held in `GitRepo.credential_host` rather than read from the checkout. A rewritten remote now produces a failed push instead of a stolen token.
2. **Host code execution.** `.git/hooks/post-commit`, `post-checkout` and `pre-push` all fire on the host during steps 5, 4 and 9; `core.fsmonitor` fires on every `status`; a `.gitattributes` `diff=X` paired with `diff.X.textconv` fires during the Reviewer's diff. `--no-verify` covers `pre-commit`/`commit-msg` only. **Partly fixed:** `core.hooksPath=/dev/null` and `core.fsmonitor=` are now in the base args; git's environment is built from an allowlist so the App private key and database URL are no longer inherited by git or anything it spawns; and its config files are pinned to `/dev/null`, so no `~/.gitconfig` or `/etc/gitconfig` is read (see the correction under "Danger 2" in `.claude/rules/verify-sandbox.md` — a tracked `.gitattributes` plus the operator's own config was a live route that none of the base args covered). `retrieval.index` carries the same pins and the same allowlist via `UNTRUSTED_TREE_CONFIG_ARGS`/`sanitized_git_env`; it remains a **separate** git wrapper from `repo.py`'s, which is a known duplication and a deliberate deferral, not an oversight.

**The second one is not properly closed, and should not be treated as closed.** Enumerating dangerous config keys is a losing game — `filter.*.smudge`, `core.pager`, `core.sshCommand`, `uploadpack.packObjectsHook` are all the same shape. The durable fix is architectural: **do not run git on the host against a `.git` the sandbox could write to.** Either restore `.git/config` and `.git/hooks` from a trusted copy after Verify, or have Verify emit a patch that gets applied in a clean clone. **Decide this together with the sandbox isolation mechanism — it is the same decision, and it also settles the "Verify in the checkout or a copy" question (settled in `.claude/rules/index-and-checkout.md`, "Checkout lifecycle").** (That decision has since been made: the sandbox receives a byte-identical export without `.git` and never writes back into the checkout. See "Danger 2" and "Byte-identical export" under "Verify sandbox" in `.claude/rules/verify-sandbox.md`.)

A note on the `argv` reasoning: keeping the token out of `argv` defends against *other users* on the host, since `/proc/<pid>/environ` is `0400` while `argv` is world-readable. It does **not** defend against root or a same-UID process. If the sandbox runs as root and shares a PID namespace, it can read the token out of the worker's environment for the duration of a clone or push regardless.

Three more things that only show up once this is real code, all now covered by tests:

- **The clone must not be shallow *or* single-branch,** and that has to be asserted, not assumed. Either flag drops the previously-indexed commit, `git diff <indexed_sha> <current_sha>` fails, and every task silently falls back to a full reindex — a cost regression that never surfaces as an error. `clone()` fails loudly if the result is shallow.
- **Killing a timed-out git means killing its process *group*,** not the `git` process, and the pgid must be captured at spawn rather than looked up at kill time. Git delegates to helpers (`git-remote-https`, and the credential helper above, which is a shell). Kill only the parent and those children keep the stdout pipe open. That strands the command two different ways: if git has not been reaped, `Process.wait()` blocks because the transport needs every pipe closed; if git *has* been reaped, `wait()` returns instantly off the recorded exit code — and `os.getpgid()` then raises, so the fallback does nothing and the orphan leaks while the timing looks perfect. Spawned with `start_new_session=True` (so pgid == pid), killed with `killpg` on the cached value.
- **Squash builds the commit before moving the branch.** The obvious `reset --soft <base>` then `commit` moves the ref first, so any failure in between strands the branch at base with every attempt commit unreachable — in a clone that is about to be deleted, at step 8, after all the work succeeded. This is reachable by ordinary means: after Verify runs a test suite the tree is full of untracked artifacts, so a net-zero branch passes a `status --porcelain` guard (which counts untracked files) and then fails `git commit` (which does not). Now: compare `HEAD^{tree}` against `<base>^{tree}` first, then `commit-tree`, then move the ref onto a commit that already exists.

**Related, and now closed:** `commit_all` stages with `git add -A`, so artifacts a test run leaves behind (`.pytest_cache`, `__pycache__`, coverage files) would get swept into the next attempt commit and into the PR diff for any repo whose `.gitignore` does not cover them. Verify runs against `export_tree`'s copy, which is a sibling of the checkout rather than inside it, so the suite never writes into the tree `git add -A` sees. Keep it that way: moving the export inside the checkout would reopen this silently, and the symptom would be a dirty PR rather than an error.

If the target branch moved while the task ran, the PR conflicts — this is where the conflict-resolution agent comes in. The per-task clone keeps that window small but not zero.

**Wired (Package C): `pipeline/repolace_pipeline/conflicts.py::merge_moved_target`, the `conflicts` stage in `run.py`.** It runs after the review and the first gate, and **only when the gate would open a PR**: a moved target matters because the PR would conflict, so a task that opens none (gate refused, `open_pr=False`, a gold run) never fetches, merges or spends the extra suite run. Order: `target_moved()`; not moved is a no-op (one fetch, one `task_stages` row). A tip already contained in HEAD (a force-push that rewound the target) is left alone, since moving the base back would put commits the target no longer has into the squash. Otherwise `merge_tree` previews; more than `MAX_RESOLUTION_PATHS` conflicted paths is `conflicting` without merging. A clean `merge_no_commit` is concluded with `commit_merge`. A conflicted one goes to the resolver only if every unmerged path's `conflict_kind` is `both_modified` or `both_added` and every path is UTF-8; the resolver's `check` is the host's (marker lines, by the same regex `commit_resolution` uses and a test holds equal, plus "nothing unmerged outside the set") and its `is_protected` is the main agent's `protected_check`. On `RESOLVED`, `commit_resolution`; a refusal there (a marker, a stray edit) is `conflicting`, a `GitError` is a harness failure. Then `advance_base(tip)` and **one more scored attempt on the merged tree** (`AttemptScorer.verify_attempt`, the next attempt number): the outcome, the diff, `changed_files`, `baseline_files` (now the new base's) and a second `pr_decision` all use it, and the pre-merge attempt stays in `task_test_runs`. The sandbox baseline is still the old base's, so the merged attempt is compared with a baseline that predates the target's own changes; the image is the one built from the old base too. A merged tree with no change against the new base (the target already holds the change) opens no PR and keeps the pre-merge score. **Anything that cannot be merged** (a non-plain-text conflict, any resolver stop but `RESOLVED`, no model client, a refused resolution): `abort_merge`, HEAD back at the scored commit, status `conflicting`, no PR, the pre-merge outcome kept, `tasks.conflict_reason` (migration 0015, a CHECK ties it to `conflicting`) a short sentence with counts and conflict kinds and no path, `error_message` NULL. A resolver raising `LLMCallError.provider_refused` propagates and fails the task like the agent's. The resolver runs under its own `TaskBudget` inside a fresh `task_scope`: half the agent budget's remaining dollars and wall clock, at most $0.50 and 600 s, and half its remaining calls, at most 40. `RunResult.attempts` and `retry_count` stay the agent's own count; the merged attempt is not a retry.

Implemented in `shared/repolace_shared/git/`: `repo.py` (the git CLI wrapper) and `workspace.py` (`task_workspace`, whose methods are steps 1 and 4–10 in order). Steps 2, 3 and 6 belong to the caller — indexing and the Verify sandbox respectively.

**Primitives for a target branch that moved after the clone** (Phase 2 plan, section 3; wired, see above). On `GitRepo`: `fetch_branch` (authenticated, forced refspec into `refs/remotes/origin/<branch>`, non-shallow asserted afterwards), `rev_parse`, `is_ancestor`, `merge_tree` (`merge-tree --write-tree --name-only -z`; exit 1 is "conflicts", any other exit raises), `merge_no_commit` (`--no-commit --no-ff --no-edit`, `merge.conflictStyle=zdiff3`), `abort_merge`, `unmerged_files` (stage modes per path; `conflict_kind` separates both-modified and both-added from delete/modify, mode, symlink and gitlink conflicts, which are not for a text resolver), `stage_paths`, `commit_merge`. On `TaskWorkspace`: `target_moved()`, `advance_base(sha)` (the one place `base_sha` is reassigned, refused unless the commit is already in HEAD) and `commit_resolution(paths, message)` (the host's check: paths confined with `resolve_within` and refused under `.git`, every unmerged path covered, no marker lines, nothing edited outside the named paths, `--no-verify`).

They go through the same pinned wrapper as everything above (`run_git_checked`, which takes an explicit set of accepted exit codes and defaults to `{0}`), so they inherit the config pins, the allowlisted environment, the process-group kill and the host-checked credential helper. A model- or remote-supplied name is never an option: a branch is validated by `check-ref-format --branch` and then sits after `--` in a refspec; a ref is resolved to a 40-hex sha before it reaches `merge`.

**These operations are where a checkout's own `.git/config` bites.** A tracked `.gitattributes` (`*.py merge=x`, `filter=x`) needs no sandbox write and selects a driver or filter; the command is in `.git/config`. Reproduced: a merge driver ran on the host during `merge-tree`, and a clean filter during `add`. So every primitive that fetches, merges, stages or commits first calls `require_trusted_config`, which **refuses** (`UntrustedConfigError`) if `.git/config` holds any key outside what `git clone` writes (`core.{repositoryformatversion,filemode,bare,logallrefupdates,ignorecase,precomposeunicode,symlinks}`, `remote.origin.{url,fetch}`, `branch.*.{remote,merge}`). A closed allowlist rather than another key list; an unreadable config also refuses. Hook files and `core.hooksPath`/`core.fsmonitor` are already beaten by the `-c` pins. `commit_all` (`git add -A`) does not call it, which is unchanged and relies on the sandbox never receiving `.git`.

**Requires git >= 2.38** (`merge-tree --write-tree`); `require_git_version` raises `GitVersionError` with the found and needed versions. Pin it in the worker image.
