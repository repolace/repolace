## Index freshness protocol (decided)

When a task starts work on an issue:

1. Read the repo's last indexed commit (`registered_repos.indexed_commit_sha`).
2. If it equals the checkout's current commit, the index is current — use it as is.
3. Otherwise index incrementally from that commit: `git diff <indexed_sha> <current_sha>`, then delete and re-chunk **only** the files that changed. Untouched files keep their existing chunks and embeddings.

Implemented in `rag/retrieval/index.py::reindex_if_stale`, single-flight per repo via a transaction-scoped advisory lock.

## Checkout lifecycle (decided)

**One ephemeral clone per task. No persistent clone cache.**

At the start of a task: clone the repo to a temp directory, index from it, let the agents work in it, and delete it when the task ends. Nothing is kept between tasks.

Why this works despite incremental indexing needing the previously-indexed commit: **chunks and embeddings live in Postgres, not in the checkout.** Throwing the tree away does not throw the index away, so re-cloning still skips re-embedding every unchanged file — which is the expensive part. And a *full* clone contains complete history, so `git diff <indexed_sha> <current_sha>` resolves in a brand-new clone. Persistence would only save download time, not correctness.

The one hard constraint: **the clone must not be shallow.** `--depth 1` cannot resolve the previously-indexed commit, so every index would silently degrade to a full reindex and `indexed_commit_sha` would never save any work. If clone cost becomes a problem on large repos, the thing to reach for is a partial clone (`--filter=blob:none`, paired with `--no-renames` on the diff so rename detection does not pull blobs back down): full commit history, deferred file contents. Measure before adopting — untested here.

**Ordering within a task matters.** Index first, from the clean checkout, *before* any agent edits it. Otherwise a reindex would capture the agent's own uncommitted work as if it were repo state and write it into the index.

Because each task gets its own clone, two concurrent tasks on one repo are isolated at the filesystem level for free. The advisory lock in `reindex_if_stale` is still needed — it protects the shared `code_chunks` rows in Postgres, which separate checkouts do not.

When the previously-indexed commit is genuinely unreachable — force-push, or an upstream `gc` — `reindex_if_stale` catches the failed diff and falls back to a full reindex rather than erroring permanently.

**Settled since (this was "still open"):** Verify runs against a copy, never the checkout. Verify executes LLM-generated code and the repo's own test suite, either of which can mutate or delete files, and the copy is what omits `.git` (see "Byte-identical export" under "Verify sandbox" in `.claude/rules/verify-sandbox.md`). The checkout also no longer contains the installation token (see "Branch and PR flow within a task" in `.claude/rules/git-and-pr-flow.md`).

Implemented in `shared/repolace_shared/git/workspace.py::task_workspace`, an async context manager that clones into a temp directory and deletes it on exit. Cleanup failures are logged, never raised: losing a temp directory is a disk leak worth seeing, but it must not replace the exception explaining why the task failed. Expect that path to get exercised once the sandbox runs as root and leaves files the worker cannot delete.

## Concurrency (decided)

Checkouts are per task, so two concurrent tasks on one repository are isolated on the filesystem for free; the shared state is the `code_chunks` rows. **The indexing-lock question is resolved with a bounded wait inside the pipeline, not with the runner's scheduling.** `reindex_if_stale` takes a *try*-lock (`pg_try_advisory_xact_lock`), so a second task on one repository is refused at once with `RepoIndexInProgress`, and that is the *normal* case for a benchmark (three runs of one instance). `_index` in `run.py` retries in 10 s steps up to a 20 min cap and then fails the stage with a message saying so; when the wait ends the index is normally current, so the task's own pass finds nothing to do. **A session must not be reused across `reindex_if_stale` calls:** the function owns its transaction (it commits, and rolls back on failure, because the lock is transaction-scoped), and `rollback()` expires every loaded ORM instance, so touching an attribute afterwards raises `MissingGreenlet` outside the greenlet; `_index` opens a fresh session per attempt. **Product limit, recorded, not fixed:** the index is per repository, not per commit (`registered_repos.indexed_commit_sha` is a single value), so two concurrent tasks on *different branches of one repository* see each other's index, which at best costs reindexing and at worst retrieves chunks from the other branch. Benchmark repositories have one branch (`main`), which is why it does not bite there.

**Worker concurrency and recovery (Phase 2).** `WorkerSettings.concurrency` (default 3) prefork children, `worker_prefetch_multiplier=1`, so one task per child and nothing parked behind a long one. Two beat jobs, `repolace.sweep_queued` and `repolace.reap_abandoned`, are routed to a **separate `repolace.maintenance` queue**: with every child busy on a multi-hour task they would otherwise never run. The **sweeper** republishes `queued` rows older than 5 minutes with `eval_run_id IS NULL`, at most once per 15 minutes per task (a Redis key `repolace:swept:<task id>`, `SET NX EX 900`), at most 50 per tick, with `retry=False`, **reading at most `WorkerSettings.sweeper_scan_limit` old rows per tick, oldest first** (750: `max_per_tick` times the 15 ticks of a dedupe window, which is all a window can act on, so a long backlog costs a bounded read and drains from the front), each republished message carrying **`expires` = the 900 s dedupe window** (a copy nobody consumed is dead before the next one is published, so a backlog never holds two live copies of one row), and **aborts the tick on the first broker or Redis error** (logged once) so an outage cannot become a publish storm; a duplicate that does get through is harmless (same Celery id, conditional claim). The **reaper** fails a `running` row whose `heartbeat_at` is older than 5 minutes (or NULL with `started_at` older than 5 minutes) as `runner: abandoned`. The staleness test is part of the UPDATE's own WHERE clause (`tasks_recovery.fail_if_heartbeat_stale`, `RETURNING`), so a heartbeat landing between its SELECT and its write leaves the row running, and it removes the task's `repolace-<hex12>-*` containers only for rows that UPDATE failed. It reaches only containers on its own docker host, so the maintenance worker must run on the host of the task workers' daemon. It warns (`worker.reaper.long_stale`) when rows are stale for more than 3x the threshold, which means the maintenance worker was down. Beat messages carry `expires: 60`. No index on `heartbeat_at` was added: the reaper reads only `running` rows, at most about K of them. `WORKER_ROLE` (`task`, the default, or `maintenance`) gates the machinery: only the task role builds `Resources`, preflights the models, warms the embedder and sweeps orphans; the maintenance worker needs only the database, Redis and docker. Task children are recycled by `worker_max_memory_per_child` (4,000,000 KiB) and `worker_max_tasks_per_child` (50). At start the task role logs its `task_time_limit` and the RabbitMQ `consumer_timeout` the broker must exceed.

**The bound is `repolace_worker.bound.bounded`, not `asyncio.timeout`, and its expiry is a `WorkerTimeout`.** `run_task` settles a cancelled row itself, before the exception leaves it, and records the *name* of what reached it (`interrupted: <name>`); `asyncio.timeout` can only cancel with a plain `CancelledError`, so a timed-out task used to read `interrupted: CancelledError` and the worker's later `worker: timeout` write (conditional on `running`) never landed. `bounded` is a thin iterator between the loop and `run_task` that throws a `WorkerTimeout` into it for the cancellation its own deadline caused, so the row reads `interrupted: WorkerTimeout` and the failed stage's error starts with the same name. `WorkerTimeout` **subclasses `CancelledError` on purpose**: the git, process and sandbox code kills child process groups in `except asyncio.CancelledError`, and those handlers must run for a timeout. The expiry is consumed with `Task.uncancel()` (as `asyncio.timeout` does), a cancellation from anywhere else passes through as a plain `CancelledError`, and it relies on the single-argument `throw` of Python 3.12+. `worker: timeout` stays as the backstop for a row whose own failure write did not land. Nothing in `pipeline/` changed for this.

**The worker refuses benchmark rows.** `run_one` reads `eval_run_id` before the claim and, if it is set, logs `worker.task.benchmark_refused`, returns `BENCHMARK_REFUSED` (acked and dropped, the row untouched). The API and the sweeper never publish those, so a message for one was published by hand, and running it would score it outside the eval runner's manifest.

**Broker timeout.** RabbitMQ closes the channel of a delivery left unacked past `consumer_timeout` (default 30 min), and an `acks_late` task holds its delivery for its whole run. `tasks.required_consumer_timeout_ms` is the hard limit plus `CONSUMER_TIMEOUT_MARGIN_SECONDS` (1,800 s: a recycled child's init before the task starts, the broker's periodic check, the reject after a hard kill) = 14,100,000 ms, `infra/rabbitmq.conf` carries that value and is mounted into the broker as `conf.d/20-repolace.conf`, and `worker/tests/test_worker_deploy_config.py` fails if the file falls below the function. Raise `WORKER_TASK_BOUND_SECONDS` and the file must follow.

**Deployment (`infra/docker-compose.yml`, written and validated with `docker compose config`, never started).** Two services from one image (`worker/Dockerfile`: git checked `>= 2.38` at build, `util-linux` for `prlimit`, the docker *client*): `worker` (`WORKER_ROLE=task`, `-Q celery`, `WORKER_CONCURRENCY` children, the only service with an env file, `infra/worker.env`, which holds the GitHub App key and the provider keys) and `worker-maintenance` (`WORKER_ROLE=maintenance`, `-Q repolace.maintenance`, one child, embedded beat, **exactly one replica**, no env file and so no provider keys). Both mount the **rootless** daemon's socket (`${DOCKER_SOCKET:-/run/user/1000/docker.sock}`) at a path of their own and set `DOCKER_HOST` to it; **the rootful `/var/run/docker.sock` is never mounted** (root-equivalent on the host; it appears only in the warning comment next to the mount, and a test fails if it appears anywhere else). The task worker's workspace (`WORKSPACE_PARENT_DIR`) is bind-mounted **at the same path inside and outside** the container, because the sandbox's `-v <path>:/repo` is resolved by the daemon on the host; a named volume would give every Verify run an empty `/repo`. Both run as container root (`user: "0:0"`) because on the rootless daemon container uid 0 *is* the unprivileged host user that owns the socket and the workspace; `init: true` reaps the children a killed process group leaves behind. The `api` service has its own `infra/api.env` (see "Exposure" in `.claude/rules/api-and-ui.md`).

**Tests.** `REPOLACE_TEST_EVAL_REQUIRED=1` turns a missing eval harness from a skip into a failure for the test that holds `DEFAULT_TASK_BOUND_SECONDS` equal to `harness.enqueue.task_wall_clock_bound()`; under `uv sync --all-packages` it is always importable, so set it in CI. On start each task worker deletes `repolace-task-*` directories under `WORKSPACE_PARENT_DIR` older than the hard time limit.
