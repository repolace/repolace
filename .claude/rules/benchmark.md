## The benchmark (decided)

Phase 1's claim is a number, so the harness (`eval/harness/`, the `repolace-eval` command) is built to make that number hard to inflate. **It exists and is tested; no sweep has run, so there is no number.** The stages in order: `select`, `fork`, gold validation (`enqueue --agent gold`, `run --agent gold`, `gold`), the sweep (`enqueue`, `run`), `report`, and separately `retrieval`.

**Instances: a filtered subset of SWE-bench Verified, not the official set** (`select_instances.py`). The allowlist of repositories (`pytest-dev/pytest`, `pylint-dev/pylint`, `psf/requests`, `pydata/xarray`, `sphinx-doc/sphinx`, `mwaskom/seaborn`, `pallets/flask`) is the maintainer's recollection of which Verified repositories are pure-Python pytest projects and only bounds what is worth cloning; **the filters decide**. `django` (its own runner) and `sympy` (`bin/test`) are out, and so are `astropy`, `matplotlib` and `scikit-learn`: the image installs into `/repo` and every run then bind-mounts the export over `/repo`, so anything an install generates *inside the tree* (a `setuptools_scm` `_version.py`, in-tree compiled extensions) is masked at run time and such a suite is unscoreable by construction. An instance must survive, in order, and the first failure is its recorded reason: a complete, untruncated row; a non-empty `FAIL_TO_PASS` and a well-formed id and `base_commit`; a test patch touching only `is_protected_path` files, adding or modifying only (no delete, rename or binary) and no dependency-manifest name; a **simple-fix filter**, meaning a gold patch that touches no protected path, no `.git*` component and nothing under `.github/` and deletes or renames nothing (the agent's edit tool refuses those paths, so such an instance is unfixable and would inflate the denominator, at the price of a set that skews toward pure source edits); an entry in the SWE-bench environment snapshot that can be built (Python 3.8 or later, or no system packages, because old Debian images have archived apt repositories); no tracked symlink or gitlink at the base commit (the byte-identical export refuses both); both patches pass `git apply --check`; every post-apply file is valid UTF-8. **Patches are applied to a git index, never a checkout**: no working tree exists, so no filter, `eol` conversion, hook or symlink can act, and the stored bytes come straight from blobs. Selection is deterministic: candidates are ordered by `sha256(seed:instance_id)` and taken round-robin across repositories under a per-repository cap (`--max-per-repo`, default 6) until `--count` (default 25) pass; the **seed (default 0) is a degree of freedom, so it must be fixed and recorded before the first agent run**. There is no automated preference for fast suites: gold validation records each suite's wall time and *proposes* `targeted_p2p`, and the maintainer prunes by hand. The SWE-bench environment snapshot, `eval/harness/swebench_specs.json`, is committed. It was generated once with the snippet in `harness/specgen.py`, pinned to `swebench==4.1.0` (later releases no longer ship `MAP_REPO_VERSION_TO_SPECS`).

**Instance files** are `eval/instances/<id>.json` (`InstanceSpec`, `shared/repolace_shared/instances.py`): the overlay (`test_files`) as **complete file bytes**, `fail_to_pass`, `pass_to_pass`, `gold_files` (the complete post-fix files, `repr=False` so a stray log line cannot print them), a raw `spec` mapping that `verify.spec.spec_from_mapping` consumes, and the `problem_statement`. The *reference fix as a diff* is a separate `<id>.gold.patch` sidecar that only the retrieval eval reads. **Be exact about what the pipeline loads:** it never loads the sidecar, but in benchmark mode it does load the instance JSON, `gold_files` included, because the gold runner needs them. Nothing hands them on: `IssueContext` and `AgentDeps` have no such field, and `shared/instances.py` states that `gold_files` "must never reach an agent, a prompt, or a tool result". An id that came from a database row is only ever resolved with `load_instance_by_id`, never by building `dir / f"{id}.json"` by hand.

**Benchmark repositories** are private `repolace/bench-<instance_id>` repositories in the existing organisation, which also hosts `repolace/repolace`; that is why the guardrails *are* the design (`harness/bench_repos.py`, run by `repolace-eval fork`). `check_bench_name` is the one decision about what may be touched, enforced a second time on every outgoing request path by an allow-list and a third time where the push leaves the process (a credential-free `repolace/bench-*` URL and exactly one refspec, `<base commit>:refs/heads/main`). **A repository the tool did not create is never adopted or deleted**: each one it creates carries a marker description, a 422 "already exists" is followed only for a private repository with the marker, and `--delete` re-reads the repository immediately before each DELETE (an earlier version recorded a pre-existing `bench-*` repository as ready and would then have deleted it). Each is created private with issues and wiki off, and **Actions are disabled before the first push**, because a workflow in the upstream tree, run by the push of the base commit, would otherwise run with that repository's own token; if any later step fails the repository is recorded `status = "incomplete"`, which only `--delete` may use. No parser accepts an abbreviated option (`fork --de --y` must not mean `--delete --yes`). **The token (`REPOLACE_BENCH_GITHUB_TOKEN`) goes inline on the one command and is never put in `.env`**: `infra/docker-compose.yml` gives the `api` service `env_file: ../.env`, so a token there lands in the environment of an internet-facing container. The module recommends a dedicated bot account that is a plain organisation member in no team that reaches the product repository, a classic `repo` token with a 7-day expiry (and `delete_repo` only for the cleanup run), and installing the App on "selected repositories"; it also says that pushing a commit that changes `.github/workflows/*` probably needs the `workflow` scope. **Every one of those GitHub-side statements is marked "confirm against GitHub's current documentation" in the source, and none has been exercised against real GitHub** (see "Unverified" in `CLAUDE.md`).

**Gold validation runs through the real pipeline, not a standalone script.** `--agent gold` writes the instance's `gold_files` into the checkout (each through `confine`, all checked before any is written) and calls `verify_attempt(1)` as an agent would; `--agent gold` forces no PR, in the CLI and in `run_task` itself. A standalone validator would re-implement clone, export, overlay, verify and score and then drift from them. The runner is run twice (`gold-1`, `gold-2`, at $0 of LLM cost) and `repolace-eval gold --runs gold-1,gold-2` writes `eval/instances/VALIDATION.md`. An instance is accepted only if both runs scored `passed`; the attempt-0 baselines are identical across the runs (a suite whose baseline changes between two runs of one commit is flaky and makes every later score ambiguous); every fail-to-pass id was **collected** at baseline (an id in no result bucket and in no module that failed to import is almost always a node-id format mismatch between SWE-bench and our plugin, and as an agent run it would be charged to the agent), checked first; and every one was **red** at baseline (`expected_not_red`). It never edits an instance file; it *proposes* `targeted_p2p` (pass-to-pass over the fix's own test files) when the longest run reaches half the suite timeout, because every task runs the suite at baseline and again after each attempt, so a suite near its timeout turns into unscoreable runs; and also when that run, padded the same way, would make a task outlast the runner's per-task wall clock (see "The sweep"). **If the gold patch does not score PASSED the instance is dropped, not "fixed"**: that is what makes the number a measurement of the agent rather than of how well an instance was prepared. Gold validation is also the cheapest experiment that retires the install-masking risk above before any LLM spend.

**What the first gold validation found (6 of 18 accepted; the other 12 were instrument failures, each addressed below and confirmed by a single-run pilot, and the second two-run validation is what accepts them).** None of them was the instance's fault, and none could have been found without a real container, which is why gold validation comes before any agent run. Each is now encoded where it belongs, so a re-selection reproduces it:

- **SWE-bench's `packages: requirements.txt` is not a tracked file.** It is something SWE-bench's own tooling assembles; at the base commits of flask and pylint nothing by that name exists. `specgen._REQUIREMENT_FILES` names the tracked file with the same test dependencies (`requirements/tests.txt`, `requirements_test_min.txt`).
- **`setuptools_scm` needs `.git`, which the export deliberately lacks.** pytest's editable install failed with "unable to detect version". `specgen._SCM_DISTRIBUTIONS` sets `SETUPTOOLS_SCM_PRETEND_VERSION_FOR_<DIST>` (per distribution: the generic variable would also reach every dependency built from source) to the instance's release. The install then writes `src/_pytest/_version.py` *inside the tree*, which the run's bind mount hides, and pytest imports it unconditionally: that is the install-masking risk recorded above, made real. `RepoSpec.generated_files` lays such files over every export (scored runs, probes and scripts) after the image is built; they are not in the image or its cache key, and not hidden paths.
- **The report plugin runs on whatever pytest the repository pins.** It read `Config.rootpath`/`inipath`, which arrived in pytest 6.0; on 5.x `pytest_configure` raised, its broad `except` dropped the recorder, and the report was empty for every pytest 5.x instance. It now falls back to `rootdir`/`inifile`, and a failed configure says so on stderr. It also ignores nested sessions (pytest's suite runs pytest in process with the plugin loaded), which would otherwise replace the outer recorder.
- **pytest's own suite needs its `pytester` plugin and no autoload.** Its `tox.ini` loads `pytester` through `addopts`, which the sandbox clears (`extra_pytest_args = ["-p", "pytester"]`), and a `typeguard` plugin vendored by setuptools registers an ini type pytest 5.x rejects, crashing every inner session (`disable_plugin_autoload`). Together these were over a thousand baseline failures, the curated fail-to-pass tests among them.
- **Dependencies drift.** sphinx 3.x imports `roman`, which docutils stopped bundling; `specgen._EXTRA_PIP_PACKAGES` adds it for 3.x only, so the 4.x environments that had already passed gold were not changed. Prefer scoping a fix to the versions that need it: changing a validated environment leaves it unvalidated.
- **An unscoreable run keeps its stderr.** stdout and stderr are captured separately and the tail used to be stdout only, so a startup crash (which reports on stderr) left an empty tail. The sphinx cause was invisible until this changed.
- **SWE-bench cuts some ids at the first space.** `test_x[a: str = None-Optional[str]]` is stored as `test_x[a:`, because its ids came from whitespace-split output. `verify.scoring.expand_truncated_ids` reads an id with an unclosed `[` as standing for every recorded id that continues it with a space, each of which must pass; one with no continuation still reads as missing. Used by `score`, `expected_not_red` and gold's collected check. Only `pylint-4551` has such ids in its fail-to-pass list; several instances have them in `pass_to_pass`, which nothing matches by id.


**The sweep** (`enqueue`, `run`). `enqueue` writes `eval/runs/<run>/manifest.json` (the repolace commit, the model, the stage models, the limits, the instances, runs per instance, the agent) atomically **before** inserting the first row, then inserts the rows idempotently (`ON CONFLICT DO NOTHING` on `uq_tasks_eval_instance_run`), all-or-nothing on resolution (an instance whose repository the App has not synced is an error that says so). It refuses a modified tracked tree (`--allow-dirty-tree` to override), because a sha that does not describe the code that runs is worse than none. `run` starts up to K (`-k`, default 3) `python -m repolace_pipeline.cli <task_id> --agent {llm,gold} [--no-pr]` subprocesses, each in its own session so a hung task is killed as a group, logging to `eval/runs/<run>/<task>.log`. **K is a RAM decision** (each child loads the embedding model and starts a container with a 2 GB limit; the source estimates about 10 GB free for K=3). **A task row is never re-queued**: `task_test_runs` is unique on `(task_id, attempt)`, so a second run of one row would fail on insert at best and mix two runs' evidence at worst. Every status write by the runner is `RUNNING -> FAILED` and conditional on the row still being `RUNNING`; this covers a child killed on the wall-clock timeout, a child that died leaving its row `RUNNING`, and `--mark-abandoned` for rows whose runner died (stale `RUNNING` beyond the timeout plus a 600 s grace, marked `runner: abandoned`). The runner refuses to start if its `--agent`, `--model` or `--timeout-seconds` disagree with the manifest. **The wall clock's default (11,700 s) is derived, not chosen** (`enqueue.task_wall_clock_bound`): the index-lock wait (1,200 s) + the environment build (2,400 s) + the baseline suite (1,800 s) + the agent's wall budget (3,600 s, which contains every scored suite that starts inside it) + one scored suite that starts just before that budget runs out (1,800 s) + 900 s for the stages no constant bounds (clone, embedder load, the task's own index pass, review, push, PR). A shorter limit would kill legitimate slow-suite tasks as `runner: timeout`, which the report counts as harness errors, so they would leave the secondary `passed / admissible` figure; a test holds each term equal to where it is defined. An instance whose spec sets a longer suite timeout needs a longer `--timeout-seconds`; `gold` proposes `targeted_p2p` when the measured suite (padded as for the suite-timeout rule) would make a task outlast the runner (`--runner-timeout-seconds`, default the runner's). `--max-total-usd` is checked before each dispatch against `SUM(llm_calls.cost_usd)` for the run, so tasks already in flight finish and the total can exceed it by up to K times the per-task cap. The child's environment is an **allowlist** (the `REPOLACE_BENCH_GITHUB_TOKEN` name is excluded explicitly), plus `GATEWAY_STAGE_MODELS` when `--model` is given; SIGINT, SIGTERM and SIGHUP cancel the run and kill the children (an earlier version left SIGTERM children running and spending). Exit codes are the pipeline's: 1 only when repolace itself broke.

**The report's headline accounting is the claim** (`eval/harness/report.py`, written down once in its module docstring and repeated beside the number). **`passed / planned`**, where *planned* is the grid in the run's manifest (`instance_ids x range(runs_per_instance)`) and **every planned row that is not a pass is a non-pass, whatever the reason**: a failure, a `passed_with_test_edit` (never a pass, approved or not), a harness error, an inadmissible row. Excluding rows after seeing the results is what a sceptical reviewer calls cherry-picking, so the headline does not; `passed / admissible` is printed only as a labelled **secondary**, with the exclusions listed. The grid is checked against the database, not the reverse: a planned row that is missing or still queued/running **withholds** the headline unless `--allow-partial`, which marks it `PARTIAL (n of m)`; a run with no manifest has no grid and is marked `UNANCHORED`. Every finished row lands in one bucket by `classify`, first match wins: unfinished, harness error (status `failed` only), inadmissible (finished, outcome NULL), `passed_with_test_edit`, `passed`/`failed`. **A stop reason of `llm_error` is not a harness error**: it covers non-transient model errors too (a context-window overflow, an unparseable replayed call), which depend on how hard the instance is, and the scorer already gives such a task an outcome, so it is counted by that outcome and shown in its own column. The interval is a percentile bootstrap **over instances** (the runs of one instance are not independent: an instance a model can fix, it mostly fixes every time, so an interval over pooled rows is far too narrow); the per-run range is the spread with the instances held fixed and is labelled as not an interval. **At N = 15 to 20 the 95% interval is about 30 to 40 percentage points wide**, and one instance moves the rate by 1/N. Marks printed on the figure: `UNCURATED` (a pass whose reason says no curated fail-to-pass list was used), `UNANCHORED`, `PARTIAL`, `NO-LLM-CALL PASSES` (a pass that made no model call is a gold or stub run filed under the wrong id), and `UNEQUAL RUNS PER INSTANCE`. A run that mixes models **withholds** its headline (a rate over two models is a statement about neither). Comparisons between models use only instances scored under both, on `run_index` 0, and print discordant counts and an **exact McNemar p-value** and no difference of rates: 8:0 gives p = 0.008, 7:1 gives 0.07, 6:2 gives 0.29, so at 20 instances a 20 to 30 point gap between two one-run models is not distinguishable from noise. A p95 is printed only from 40 points up. Cost and latency are **censored** by the $2 cap and the wall-clock limit (a task stopped by either shows the limit, not its cost to finish), and latency is claim-to-completion with the sweep's parallel contention in it. `--predictions` exports SWE-bench-format predictions for a cross-check with the official harness, which uses different pass criteria (node-id format, pass-to-pass scope, collection-error handling), so exact agreement is not expected.

**Contamination and honesty disclosures, which must travel with any number.** The instances are a filtered subset of a public benchmark that models have **probably seen**, so the number is **not the published Verified score** and does not predict performance on unseen issues. The prompt omits the issue number, URL and `instance_id`, but **the issue text itself can carry upstream identifiers** (a repository name in a traceback path, a linked issue), and a model that recalls the upstream fix from training is indistinguishable, in the pass rate, from one that derived it. Controls recommended and **not implemented**: a second set of issues filed after the models' training cutoffs, reported separately; the similarity of the agent's diff to the gold patch; an "edits before exploring" signature in the trajectory (a model that edits without reading is probably recalling); and no outcome-bearing text pushed to the bench repository (already held for commit messages, and a benchmark PR body carries counts, never test ids). The report prints the contamination, subset and small-N caveats beside the headline; the subset caveat lists the five ways the subset differs from Verified (allowlist, simple-fix filter, round-robin cap, gold-validation pruning, the seed).

**The retrieval eval** (`repolace-eval retrieval`, `eval/harness/retrieval_eval.py`) is planned before it spends: `--plan` counts chunks and prints the bill, and a real run refuses if `repos x strategies` exceeds `--max-index-equivalents` (default 35) and skips, loudly, any repository whose first index exceeds `--max-chunks-per-repo`. **A repository is skipped whole, never trimmed**: a smaller corpus than production searches would make every recall number look better than it is. Eval rows are made invisible to the product (a synthetic installation id -1, negative `github_repo_id`, `is_active=False`); a test pins that the API's sync never touches them. The metrics credit the *innermost* overlapping chunk, a query with no old-side gold (a patch that only adds files) is skipped and counted rather than scored as a miss, and the switch rule is in "Open questions" under embedding truncation.
