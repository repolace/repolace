## UI (built)

Server-rendered Jinja2 + HTMX + plain CSS, served same-origin by the API app (`api/repolace_api/ui/`): no node build, no CORS, no client-side framework. The visual spec is `ui/DESIGN.md`; where it and this section differ, this section is what was built. **Seen only through rendered HTML and tests, never in a browser** (the build had none): layout, focus rings and the HTMX swaps are unverified by eye.

- **Routes** (all HTML, under `/ui`; `/` redirects to `/ui/repos`; repos are addressed by UUID, not `owner/name`): `/ui/repos`; `/ui/repos/{id}/tasks?status=&outcome=&benchmark=` (outcome also takes `unscored`, which is `outcome IS NULL`); `/ui/repos/{id}/tasks/more?cursor=` (load-more rows, the same opaque cursor as the JSON API); `/ui/repos/{id}/tasks/new` with fragments `.../new/issues?q=` and `.../new/confirm`; `POST /ui/repos/{id}/tasks` (303 to the task); `/ui/tasks/{id}`; polled fragments `/ui/tasks/{id}/row` and `/ui/tasks/{id}/live`. A running or queued row, and the detail page's `#live` region, poll every 3 s; the fragment answers **286** once the task is terminal, and a task that is already terminal renders with no `hx-trigger` at all.
- **One source of truth.** The pages call the functions the JSON routes call (`query_task_page`, `load_task_detail`, `compute_estimate`, `enqueue_task`, `fetch_issues`, `fetch_branches`, in `routes/repos.py` and `routes/tasks.py`); there is no HTTP round trip to our own API. Benchmark scrubbing lives in `load_task_detail` (and `list_item` for list rows), so no page can forget it. Added to the JSON: `repo_full_name`, `cost_so_far_usd` (the `llm_calls` sum while a task has no terminal cost) and `is_benchmark` on the task detail, `is_benchmark` on list items, and benchmark list rows now have `error_message` nulled.
- **Vocabulary.** Status is a pill (`badge`), outcome is a square outlined `chip`, always two elements, always icon plus the exact enum value; `unscored` is the label for a NULL outcome and is not an enum member. Stage states are `running|ok|failed` from `task_stages` plus UI-derived `pending` and `skipped`; the word `passed` is reserved for the outcome. Plan is always shown greyed, "not used yet". Tests iterate the enums so a new status, outcome, stop reason or stage name fails them rather than rendering blank.
- **What the six statuses mean (unchanged from the mock).** `completed`: the pipeline ran to the end and opened no PR (read `outcome` and `agent_stop_reason` for why; `completed` with a NULL outcome and no stop reason is the inadmissible case, where the agent never ran). `failed` is reserved for "repolace itself broke" and is the only status that sets `error_message`. `conflicting` is in the enum and nothing sets it until the Phase 2 conflict loop. **`merged` was replaced by `pr_opened`**: whether a PR merges is branch protection's business, and nothing subscribes to PR webhooks, so `merged` was a state the pipeline could never reach; add it back only with the webhook that could set it. Status is not outcome: a row can read `pr_opened` and still be `failed`, so the list shows both and the row says "PR opened despite failing score".
- **Enqueue flow:** pick issue, pick branch (default preselected, an unknown branch is the API's 422 shown as a form error), confirm panel with the computed estimate and its basis (`repo`, `model` or `none`, low-history flagged), start. The issue list is filtered locally from a 60 s cache of GitHub's list.
- **Account page and billing (auth exists, narrowly).** `/ui/account` shows plan, status, period end and tasks used this month against the allowance, with Upgrade (posts `/billing/checkout`), Manage billing (`/billing/portal`), Sign in with GitHub (GET `/auth/github/login`) and Sign out (`/auth/logout`); a nav link is on every page. Checkout success/cancel and portal return URLs point at it; `?checkout=success|cancelled` only picks a notice and is **never proof of payment** (the plan is the `subscriptions` row the verified webhook maintains). Sign-in is a signed, HttpOnly, SameSite=Lax cookie (`routes/auth.py`, `sessions.py`); `/billing/*` POSTs and `/auth/logout` use the same same-origin check as the enqueue form. **That is all auth covers:** the JSON API and every other `/ui` page stay unauthenticated. `/billing/webhook` joins `/github/webhook` and `/healthz` as an exact-path Host-allowlist exemption (Stripe signs the raw body; Stripe sends the public name as `Host`).
- **Allowance semantics.** `tasks.user_id` (migration 0019, nullable, ON DELETE SET NULL, index `(user_id, created_at)`). `enqueue_task` takes an `owner_id` that the `enqueue_owner` dependency supplies **only when `BillingSettings.signin_ready` and a user is signed in**; then it takes a per-user advisory lock, counts that user's non-benchmark tasks since the first of the month (UTC, failed tasks included) and refuses with 402 at the plan's limit (free 5, pro 100; preview numbers in `billing_limits.py`). Otherwise there is no owner and no limit, so the benchmark runner, the CLI and installs without sign-in are unchanged. The UI enqueue form shows the 402 as its form error. Setup: `docs/BILLING_SETUP.md`.
- **No Approve action** (no auth for it until Phase 4). A `passed_with_test_edit` task shows its justification and either "awaiting sign-off" or who approved it, read-only, and never in the pass colour.
- **Benchmark tasks** are hidden from the list behind an `include benchmark` toggle, tagged when shown, and their oracle fields (`score_reason`, `patch_diff`, `changed_files`, `error_message`, test-edit justification, stage errors) are the same nulls the JSON detail route returns.
- **Derived honestly, or dropped:** short task id is the first 8 hex characters of the UUID; no per-status counts, container ids, worker names, peak memory or exit codes; the failing test name in the test-runs table is dropped (the JSON carries counts only, never node ids); "Test" duration is the baseline stage plus the scored runs, "Edit" is the `agent` stage minus those, because scored suites run inside `agent`; conflict files are not recorded (`conflict_reason` does not exist yet).
- **Diff** is parsed on the server (`ui/diffview.py`) and highlighted with Pygments' lexers, but the markup is built by the UI from escaped tokens and a fixed class table, never from Pygments' HTML formatter, and reaches the template as `Markup`, so no template uses `|safe`. Capped at 2,000 lines or 300 KB.
- **Security headers and CSRF.** Every `/ui` response carries `Content-Security-Policy: default-src 'self'` (no inline script or style, no remote origin, `frame-ancestors 'none'`), `nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: same-origin` (not `no-referrer`: with that a browser sends `Origin: null` on a same-origin POST). Templates carry no `style=""` (bar widths are SVG attributes) and no inline handlers; htmx runs with `allowEval: false` and `includeIndicatorStyles: false`. The one state-changing HTML request, the enqueue POST, requires `Origin` (else `Referer`) to match `Host` and refuses a request with neither; `Sec-Fetch-Site: cross-site` is refused too. **The limit:** this stops cross-site forgery only. There is no authentication, so anyone who can reach the port can enqueue a task with a hand-built request (and the JSON API is unguarded), which is why:
- **Host allowlist (DNS rebinding).** Every request, UI and JSON alike, must carry a `Host` on `UI_ALLOWED_HOSTS` (default `localhost,127.0.0.1,[::1]`; add a tunnel hostname there) or it gets a 400, and the enqueue same-origin check compares `Origin`/`Referer` against that list, never against `Host` (a rebinding page controls `Host`). Malformed `Origin`/`Referer` is refused, not a 500. Security headers also go on unhandled 500s. **Exempt, by exact path: `/github/webhook` and `/billing/webhook` (each authenticated by its HMAC signature, and the sender uses the public name as `Host`) and `/healthz`.** Everything else, including the unauthenticated JSON API, still needs an allowed `Host`, so exposing the webhook does not expose the UI.
- **Highlighting is allowlisted and budgeted.** Only 16 extensions are lexed (the file name is agent-chosen and some Pygments lexers are quadratic on a short line), lines over 300 characters are plain, a diff gets 2 s of highlighting in total before the rest is plain, and the work runs in a threadpool. Only `https://` URLs from the database become links. The enqueue body is capped at 16 KB by `Content-Length` and while streaming.
- **Error text can contain host paths** (sandbox and pipeline errors are stored verbatim after secret scrubbing, not path scrubbing), and the failed-task page shows it. Another reason the UI is localhost/tunnel-only until auth exists.
- **Exposure.** Until RBAC (Phase 4) the UI and API are for localhost or a private tunnel. Bind to 127.0.0.1, and the `api` container has its **own env file**, `infra/api.env` (gitignored; `infra/api.env.example` is committed), not the repository `.env`, so provider keys never sit in the environment of the process serving it. The example lists exactly the fields of `ApiSettings` and `UiSettings` (database, Redis and broker URLs, the GitHub App id, slug, private key and webhook secret, `API_BASE_URL`, `UI_ALLOWED_HOSTS`), and `api/tests/test_api_env_example.py` holds the two equal in both directions, so a new setting that is not in the example, or a provider key pasted into it, fails a test. Compose's own `environment:` sets the three service URLs and wins over the file. Done in code, **not started in a container** (no daemon in the session that wrote it).
- **Assets** are vendored and pinned (`api/repolace_api/ui/static/README.md` records versions, source URLs and the htmx sha256; a test checks the hash). No CDN at runtime. Fonts are the IBM Plex latin subset; the OFL text ships beside them. Theme is `prefers-color-scheme` by default with a system/light/dark toggle in `theme.js`, stored in `localStorage` inside try/catch.

## API (decided)

Every route has a Pydantic response model (`api/repolace_api/schemas.py`); status and outcome are the DB enums, so the JSON vocabulary is the database's. Routes: `GET /repos`; `GET /repos/{id}/issues` (number, title, html_url, plus labels as names, author login and created_at); `GET /repos/{id}/branches` (name, `default`); `POST /repos/{id}/tasks` (422 when an explicit `target_branch` is not a branch on GitHub; empty is 400; **409 when the issue already has a `queued` or `running` non-benchmark task for that branch**, since a double click would otherwise open two PRs and spend two budgets; GitHub failures are 502); `GET /repos/{id}/tasks?status=&outcome=&limit=&before=&include_benchmark=` returns `{items, next_cursor}` (keyset on `(created_at, id)` through an opaque base64url `cursor`, limit 1-100 default 50, 404 unknown repo, 422 bad enum or malformed cursor); `GET /repos/{id}/tasks/estimate`; `GET /tasks/{id}` (the full row, `attempts`, `task_stages` ordered by start, and per-attempt test-run counts, never node ids).

Decisions: stage status is `running|ok|failed` and the UI derives skipped/pending from absent rows; benchmark tasks (`eval_run_id IS NOT NULL`) are hidden from the list unless `include_benchmark=true`; there is no approve action, only the stored approval fields; diff highlighting is the UI's job. The estimate returns p50/p90 (`percentile_cont`) with `basis`: `repo` (last 30 priced non-benchmark tasks of the repo, at least 5), else `model` (the last 30 such tasks, on any repo, whose latest `llm_calls` row has the model of the repo's latest task that has one, again at least 5; the window is ordered `created_at DESC, id DESC`), else `none` with `upper_bound_usd`, the $2.00 per-task cap, kept as `TASK_COST_CAP_USD` in the API because the API image must not import the gateway (change both together). `GET /tasks/{id}` (and the HTML detail, `/live` and `/row` that poll it) loads the row **without** `patch_diff`, `score_reason` and `issue_body`: a live (`queued`/`running`) task has no value for the first two yet (the pipeline writes them in the UPDATE that ends the task), `issue_body` is not in the response at all, and a benchmark task's are scrubbed, so they are read, in one extra query, only for a finished product task. The response is the same as when the whole row was loaded; `api/tests/test_api_detail_poll_db.py` reads the statements the engine sent to prove it. `GET /tasks/{id}` nulls `score_reason`, `patch_diff`, `changed_files`, `error_message`, `test_edit_justification` and stage errors for benchmark tasks (they can name hidden tests) and never returns `claimed_by`. The branch check falls back to `GET .../branches/{name}` when the branch listing hit its page cap.


## Public site

A second ASGI app, `api/repolace_api/site/` (`create_site_app`, entry `repolace_api.site.main:app`, port 8100, compose service `site`, env file `infra/site.env`, template `infra/site.env.example`). It serves the landing page, `/pricing`, `/benchmark`, `/retrieval-benchmark`, `/privacy`, `/terms`, the waitlist form (`GET/POST /waitlist`, `/waitlist/thanks`), `/healthz` and `/assets`. **It is the only thing a public hostname or tunnel may point at.**

**Deployment (written, not yet run; nothing is deployed until the user does the steps in `infra/aws/README.md`).** The site is meant to run off the laptop on one small AWS VM (CDK stack `RepolaceSiteStack` in `infra/aws/`, arm64 `t4g.small` by default, architecture is a context parameter, AMI pinned by the required `ami_id` context; Postgres and docker volumes on a separate retained, snapshotted data volume; termination protection; minimal user data so editing the scripts never replaces the instance; ECR tags immutable; workflow actions pinned to shas), as three compose services (`infra/aws/compose.site.yml`): `site` (the same image as `api`, from ECR), `site-db` (`postgres:16`, a named volume; `init.sql` is alembic 0017's DDL plus the INSERT-only role `repolace_site`) and `cloudflared`. The security group has no inbound rule, IMDSv2 is required, access is SSM only, nothing is published on a host port, and `SITE_TRUST_CF_IP` stays true (the connector is a private peer).
- **The tunnel stays locally managed.** `repolace-site` (id `5babc1c9-6e2b-489f-9e65-890ac7ec3cbd`) keeps its credentials JSON; the VM gets it from the Secrets Manager secret `repolace-tunnel-credentials`, and the ingress (`http://site:8100`) is committed in `infra/aws/cloudflared/config.yml`. Never run two connectors for it. The other secret is `repolace-site-env` (the `site.env` content). Both are created by hand in the console; code references them by name only.
- **Pipeline: `.github/workflows/deploy-site.yml`, gated by the repository variable `SITE_DEPLOY_ENABLED == 'true'` on every job**, so merging it does nothing until the variable is set after the cutover. Push to `main` with a paths filter, or `workflow_dispatch`. Jobs: `test` (ruff, the site tests), `build` (native arm64 runner, push to ECR, tag = full sha, `GIT_SHA` build arg), `deploy` (environment `production`, SSM `AWS-RunShellScript` running `/opt/repolace/deploy.sh <sha>`, polled to completion).
- **Two OIDC roles, because GitHub's subject differs with and without `environment:`.** `repolace-site-build` (ECR push only) trusts `repo:repolace/repolace:ref:refs/heads/main`; `repolace-site-deploy` (`ssm:SendCommand` on the one instance and the `AWS-RunShellScript` document, plus `GetCommandInvocation`) trusts `repo:repolace/repolace:environment:production` and the claim `job_workflow_ref` = `repolace/repolace/.github/workflows/deploy-site.yml@refs/heads/main`; the `production` environment must restrict deployment branches to `main`. No static AWS key exists.
- **Version proof.** The image bakes `REPOLACE_GIT_SHA`; `/healthz` returns `{"status": "ok", "sha": ...}`. `deploy.sh` requires the new sha on localhost (inside the container) and on the public URL (`?cb=<ts>`), retrying about two minutes, and on any failure rolls back to the previous tag and exits non-zero. It refreshes its own files from `/repo/infra/aws` in the image (`.dockerignore` re-includes `infra/aws`), prints no env values, and sets the database role's password from `SITE_DATABASE_URL` through a psql variable.
- Backups: a systemd timer streams `pg_dump` to a versioned, encrypted, private S3 bucket (30-day expiry).


- **Public and private are separate processes, not a Host allowlist.** The site mounts no router from `repolace_api.routes` and not `repolace_api.ui`, and a test imports it in a clean interpreter to prove neither is loaded. `/ui`, `/repos`, `/tasks`, `/github/webhook`, `/docs` and `/openapi.json` answer 404 there. Never add the public hostname to `UI_ALLOWED_HOSTS`: the API and task UI have no authentication (see "Exposure" above) and `POST /repos/{id}/tasks` spends provider money and runs code on the host. The webhook GitHub calls still needs its own public route; that is a separate decision, not part of this app.
- **`/benchmark/` is a static site, a copy of `BENCHMARK/site/` from the `feat/benchmark-site` branch** (`site/benchmark_site/`, see its README for every change and the vendored D3 7.8.5 hash). It replaced the Cloudflare Worker `repolace-benchmark`, which had owned the whole hostname as a custom domain (that is why `cloudflared tunnel route dns` failed with code 1000: retire the Worker's custom domain, then add the CNAME). It had to change to run under the site CSP: the inline theme script is `js/theme-init.js`, D3 is vendored, `el()` sets `style` through `style.cssText`. The landing and pricing numbers come from `site/data/results.json`, a copy of `BENCHMARK/analysis/results.json` (`scripts/snapshot_benchmark.py`; a test fails on drift). The private `scripts/visual_report/server.py` (live sweeps, `docker exec psql`) stays on Tailscale.
- **Copy rules.** The headline everywhere is the official sweep-4 figure, 29 of 54 (53.7%), with its 35 to 72% interval and the caveats (public SWE-bench Verified, 18 issues, first measurement, PR opening not measured). The 35/54 (64.8%) figure is a hand-stated substitution of lost rows by their re-run; it appears only labelled as that (the report's comparisons use it as their baseline) and never as a headline. Tests hold this.
- **`/retrieval-benchmark/` is a second static report, mounted the same way** (`site/retrieval_site/`, `StaticAssets(..., html=True)` in `app.py`; `/retrieval-benchmark` redirects to `/retrieval-benchmark/`). It borrows from `benchmark_site/` by absolute path instead of copying: `@import url("/benchmark/style.css")` (so the tokens cannot drift; `test_site_design.py` fails if it redefines a shared token), the fonts, `js/vendor/d3.min.js`, `js/theme-init.js` and `js/core.js` (figure shell, table twin, tooltip). The two directories must therefore stay mounted together. Its data is `data/retrieval.json` (schema beside it), written by `BENCHMARK/analysis/retrieval_stats.py`; the page handles the `ready` and `awaiting` states and shows a banner for `synthetic: true`. The two reports link to each other from their footers. See `retrieval_site/README.md`.
- **One design system with the benchmark report.** `site/static/site.css` carries the report's tokens (`--page --surface --ink --ink-2 --muted --grid --axis --border --wash --accent --accent-ink --shadow --serif --sans --mono --gutter --ease`, light, dark media query and `[data-theme="dark"]`) and loads its fonts (Fraunces, Geist, Geist Mono) from `/benchmark/fonts/`, so there is one copy of each font. `api/tests/test_site_design.py` fails if a shared token differs between `site.css` and `benchmark_site/style.css` (the report's `--s-*`, `--stage*`, `--on-fill`, `--nav-h` are deliberately not shared). Both use the localStorage key `theme` and a byte-identical `theme-init.js`, so a visitor's light or dark choice carries between `/` and `/benchmark/`; the report's top bar, menu and footer link back to `/`, `/pricing`, `/waitlist`. Body text uses `--ink` or `--ink-2`; `--muted` (about 3.4:1 on the page) is for placeholders only. The hero stagger is CSS classes (`.rise-1` to `.rise-4`), never an inline `style`, because the CSP forbids it. Contrast was measured from the rendered page in both themes (64 text elements, none below AA).
- **The logo is the wordmark** (live Fraunces text, weight 560, opsz 72, in both top bars) with a favicon of a serif `r` on the accent tile; there is no icon mark, on purpose (`docs/brand/README.md` says why and how to regenerate the outlined files). The favicon, apple-touch icon and `/favicon.ico` are served by the site and versioned with the CSS (`?v=`).
- **Pricing is a preview** (`site/content.py::PLANS`): no checkout, no payment code, no payment provider chosen. The numbers are hypotheses to be validated against a real PR-opening run, confirmed Vertex console rates and a pass rate on non-benchmark repos.
- **Waitlist.** `waitlist_signups` (migration 0017): unique lower-cased email, `consent`. A repeat signup is a silent no-op that looks like a first one. Defences: same-origin check, 8 KB body cap, hidden honeypot, in-memory sliding-window limit (5 per IP per hour, 300 per hour overall), optional Cloudflare Turnstile (both keys set turns it and its CSP origin on; verified server-side with `success` and the hostname). `CF-Connecting-IP` is trusted only from a loopback or private TCP peer. The site's database role can INSERT into `waitlist_signups` and nothing else (`SITE_DATABASE_URL`; unset, the form answers 503). **The insert is a bare `ON CONFLICT DO NOTHING`**: naming `(email)` as the conflict target makes Postgres demand SELECT on that column, so an insert-only role gets `permission denied` (found by running it; the first version 500ed). Verified end to end against the compose Postgres: signup 303, repeat identical and stored once, no consent 400, cross-site 403.
- **Seen in Chrome (desktop and phone width):** landing, pricing and the benchmark report render, no console errors, no horizontal overflow. **Not verified:** dark mode on landing and pricing by eye, the Turnstile widget under the CSP, and anything through Cloudflare.
