- **Embedding truncation — the most serious known limit on retrieval quality.** The chosen model's `max_seq_length` is **128 tokens**, which is very small for code. Measured by real tokenization over this repo's own 238 chunks: **99 (41.6%) exceed the budget** and are silently truncated, embedded from their opening tokens alone. Median chunk is 105 tokens — the *typical* chunk sits just under the ceiling, so the corpus is crowded against it. By type: functions 52.7% over (median 131, already past the limit), module 46.9%, class_skeleton 33.3%, method 30.4%. The longest chunk is 1328 tokens, 10.4x the budget; `CodeChunk`'s own skeleton is 771 tokens, of which the encoder sees 128 — **83.4% never reaches it**, cancelling most of the benefit of enriching class skeletons. (Chunk counts depend on the corpus snapshot: measure again rather than quoting a figure.)

  **This is set up as a benchmark variable, not a guess.** `rag/retrieval/strategies.py` implements four interchangeable strategies (`truncate`, `head_tail`, `windows`, `signature_docstring`), selected via `embed_texts(..., strategy=...)`. **The strategy is now threaded through indexing and search** (an earlier revision of this note said the harness "should" run the grid because it was not): `reindex_if_stale`/`index_repo` take `strategy`, `hybrid_search` takes `query_strategy`, and `PipelineSettings.embedding_strategy` (default `truncate`, so changing nothing changes nothing) is what the pipeline passes to both. **`registered_repos.index_strategy` records what an index was built with** (NULL means the legacy `truncate`), because without it a repo whose commit is current would never reindex after a strategy change and old and new embeddings would mix in one index. A mismatch therefore forces a **full** reindex, not an incremental one; the field's own comment warns that a different `embedding_strategy` forces that on every repo it meets, which is why the default must stay `truncate` until the eval picks a winner. `repolace-eval retrieval` runs the grid (4 index strategies x 2 query strategies, `truncate`/`head_tail`) against gold-patch hunks with no LLM call, and **the switch rule was stated before any number exists**: a cell replaces `truncate`/`truncate` only if its paired chunk-MRR gain is at least `--min-gain-pp` (default 10 percentage points) **and** the 95% bootstrap interval over instances excludes zero. It is one of eight cells compared on the same few instances the agent is benchmarked on, so a winner is exploratory. The chunk metrics credit only the *innermost* chunk overlapping a gold hunk: a class skeleton's span is the whole class and the module chunk's span runs from its first to its last top-level statement, so crediting any overlap would score a hit when only a chunk whose content does not contain the changed line was retrieved, inflating chunk recall in a strategy-dependent way. No retrieval number has been measured yet. Measured over this repo (238 chunks, limit 128) — "still truncated" is the share of embedded texts still over budget, "encoder tokens" is tokens fed to the encoder as a share of original content, which exceeds 100% for `windows` because overlap feeds some tokens twice:

  | strategy | passes/chunk | still truncated | encoder tokens | trades away |
  |---|---|---|---|---|
  | `truncate` (current) | 1.00 | 41.6% | 54.4% | everything past the head |
  | `head_tail` | 1.00 | 0% | 54.4% | the middle of the body |
  | `windows` | 2.05 | 0% | 120.4% | 2x indexing cost; risks blurring long chunks toward the centroid |
  | `signature_docstring` | 1.00 | 0% | 32.4% | the body entirely — weakest on undocumented code, where bugs live |

  The orthogonal axis is the model itself: a 512-token context would cover the large majority of chunks outright and can be combined with any strategy. Evaluate it as a second variable in the grid rather than a fifth strategy.

  Do not estimate truncation from character counts: code tokenizes far denser than 4 chars/token (closer to 2.5 here), so a `len(text) > 4 * max_seq_length` estimate miscounts everything between ~320 and 512 characters as fitting. `embed.py` tokenizes to count.
