## Verify extensions for an agent (decided)

Verify was first built for a pipeline that ran the suite twice. An agent that reads test output and runs code needs more, and each addition is a new way for it to learn something it must not, or for one run's result to be mistaken for another's. The rules below exist for those two failures.

**Three kinds of run, with deliberately different rules** (`verify/verify/stage.py`):

| | scored (`Verifier.run`) | probe (`run_subset`, the `run_tests` tool) | script (`run_script`, the `run_python` tool) |
|---|---|---|---|
| key | `int` attempt: 0 baseline, 1..N | `probe-<n>` | `script-<n>` |
| hidden-test overlay | yes, every scored run | **never** | **never** |
| recorded in `task_test_runs` | yes | no | no |
| counts toward the "baseline already ran" guard | yes | no | no |
| source mount | per spec (`repo_readonly`) | per spec | `:ro`, unconditionally, not via a spec field |
| directories | kept with the workspace | `discard`ed in a `finally` | `discard`ed in a `finally` |

A `str` label must start with a letter and be at most 64 characters, so it can never read as an attempt number (`"1"` would otherwise give the same directory and container name as the int 1). Counters only advance, so a label is never reused, not even after its run was discarded: the export is written in place and the plugin *appends* to `report.jsonl`, so a reused label would mix two runs. A probe needs the environment the baseline built and raises `VerifierNotReady` rather than building one from a tree the agent has already edited (that would break "built once, from the base commit"). A `SandboxError` from a probe or script is **returned** (`SuiteResult.error`, `ScriptResult.error`), never raised; `VerifierNotReady` is the only exception, so the tool layer has exactly one thing to catch. A scratch script is written beside the report, outside both the checkout and the export, and is mounted read-only at a fixed path with a file name no repository has (`/scratch/_repolace_script.py`), because `sys.path[0]` is the script's own directory and a script called `main.py` would shadow a repository module. The checkpoint commit before a probe lives in the *tool*, not the verifier, so `verify` stays git-free.

**The hidden-test overlay** (`verify/verify/overlay.py`). A benchmark instance carries the test files its fixing PR added or changed. They are laid over the *export* at run time, after the environment is built, so they are never baked into an image layer the cache shares and are not in the cache key. Values are **complete file bytes**, not a diff: SWE-bench ships `test_patch` as a diff, instance preparation applies it once on the host and stores the resulting files, so nothing at run time parses or trusts a patch. Every key goes through `resolve_within` and is refused if absolute, containing `..`, containing a `.git` component at any depth, a backslash or NUL, non-canonical, under a symlinked or file parent, an existing directory, or nested under another key; nothing is written if any key is bad, and the keys are validated when the `Verifier` is constructed so a bad one fails before a forty-minute build rather than after it.

**Two verdicts, one set of preconditions.** `score()` is the benchmark's: it returns an outcome, or *inadmissible* when the instrument failed. `agent_verdict()` is the non-benchmark PR gate: `ok` means only "no regression, silenced failure or new collection error was found", never "the issue is fixed". `score()` cannot be the gate because it is inadmissible whenever nothing was red at the base commit, which is the normal case for a live issue (the suite passes; the bug is simply not covered), so under it a real task would never open a PR. Both call `_preconditions` (disqualifying paths, unusable baseline, infrastructure error, unscoreable attempt, fingerprint drift), and `TestAgreesWithScore` pins that they report the same reason, so the PR gate and the benchmark cannot disagree about what a run means. `expected_not_red(baseline, expected)` returns the curated fail-to-pass ids that were **not** red at the base commit. Without it, an expected test that already passes in our environment lets every other condition of `score` be met by a patch that changes nothing, and a comment-only edit would score PASSED. The pipeline checks it **before the agent runs** and completes the task as inadmissible if it is non-empty; the gold analysis checks it per instance.

**`is_protected_path(path, *, collected_files, conftests)` is what the edit tools refuse to write**, and the pipeline passes a baseline-aware version (`protected_check` in `pipeline/repolace_pipeline/agent_context.py`) as `ToolContext.is_protected`. The context's default is the baseline-blind function, which would let the agent edit a file pytest collects through a custom `python_files`, after which the scorer discards the whole patch. Two directions, stated so nobody "fixes" either: it is **never weaker** than `disqualifying_paths` (a test asserts it over a grid of paths), and it is **stricter on purpose**: at edit time it has no `baseline_files` evidence, so it refuses a shipped module like `django/test/client.py` that the scorer would spare, which means an issue whose real fix lives in such a module cannot be fixed by the agent. It also protects `.github/`, which the scorer does not. The baseline it is built from has the benchmark overlay's paths **removed**: a refusal that said "that file is read-only" for a path the agent has never seen would be an existence oracle for a hidden test file. The cost is accepted: an agent that writes over a hidden collected file wastes an attempt, because the scorer, which reads the unfiltered baseline, disqualifies it.

**Pytest argv, and why each addition is there** (`build_run_argv`; every pytest run, baseline, attempt and probe, gets the same ones):

- `--rootdir=/repo`, always. With no ini file pytest derives rootdir from its arguments, so a run given `tests/test_a.py` can root at `/repo/tests` and every node id lose its prefix; a probe's ids would then match nothing the baseline recorded. One rootdir is one node-id space, and the plugin fingerprints `rootdir`, so the baseline/attempt comparison cannot drift on it. (This changes the fingerprint's `rootdir` for runs recorded before it; none existed outside tests.)
- `-o cache_dir=/tmp/.pytest_cache` (already recorded above) and `-o addopts=` unless the spec keeps its own.
- `--continue-on-collection-errors`, unconditional and not a spec field. Without it pytest stops the whole session at the first collection error (exit 2, nothing run, `passed` empty): a module the patch broke, or a hidden module that cannot be imported, would hide every other result, two attempts differing only in whether a hidden file imports would give the agent different feedback, and `new_collect_failures` and the baseline's own broken modules would be dead code. With it the run exits 1, `collect_failures` is populated and the rest runs. **This is more lenient than SWE-bench, where any collection error kills the run**, so a score from this harness is not interchangeable with one from theirs, and the report's predictions export (below) is a cross-check, not an equivalence.
- The per-run nonce reaches the container as `-e REPOLACE_RUN_NONCE` (the **name only**); the value is in the docker CLI's own environment, which the CLI forwards. Argv is world-readable (`ps`) and is logged on a timeout, the same reason the git credential never travels in argv.

**Report integrity: the confused deputy again.** The sandbox owns the results directory the host later reads `report.jsonl` from, so whatever is at that path is whatever the code under test left. Review found that `parse_report` followed a symlink there: a probe (which does not carry the overlay) could point it at *another run's* report, such as the baseline written **with** the hidden tests laid over, and the host parsed it as the probe's own and handed the hidden node ids and outcomes back through the `run_tests` tool. Reproduced against the parser, with no Docker; that the sibling's host path is discoverable from inside the container (via `/proc/self/mountinfo`, which shows the bind source) rests on standard Linux behaviour and was **not run inside Docker**. A second route, an error message that carried a host path (a `chmod 000` report), was found in the same review and closed with it. The class is the one this file already names: nothing escaped, the sandbox wrote a file and the host voluntarily read it. **Now:** the host opens the report with `O_NOFOLLOW | O_NONBLOCK`, refuses anything that is not a regular file by `fstat` on the descriptor (so the thing checked is the thing read), caps its size (`MAX_REPORT_BYTES`, 64 MiB), and requires the per-run nonce on the plugin's `start` and `session` records, so a report from another run is refused even if the symlink check ever regresses (a hard link cannot cross bind mounts). The nonce is integrity against *substitution*, not authentication of the code under test: that code shares the container and its environment with the plugin, so a forged report written by the same run is accepted, by design. See the residual risks under "The no-oracle protocol".
