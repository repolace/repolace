## Task bookkeeping (migrations 0012 to 0015)

- **0012:** `llm_calls`, `tasks.issue_body`, and the nullable benchmark columns `tasks.eval_run_id`, `instance_id`, `run_index`. **`llm_calls` lives in Postgres** for the reason `task_test_runs` stores raw sets: cost, latency and the trajectory *are* the benchmark's evidence, and none can be recovered once the call is over (a cost not captured then cannot be re-priced later without re-running, and a trajectory cannot be inspected once the clone it came from is gone). Benchmark rows are queryable from `tasks` itself rather than from a second store that could drift. The price is that the table holds repository source verbatim, which matters for private repositories (redaction strips credential-shaped strings and the exact keys the gateway holds, not code). `llm_calls.cost_usd` has eight decimals where `tasks.cost_usd` has four, because a cheap-model call prices in thousandths of a cent.
- **0013:** `tasks.patch_diff`, `tasks.score_reason`, `tasks.agent_stop_reason` (a string behind `ck_tasks_agent_stop_reason` with the eight values, not a Postgres enum, so adding one is a drop-and-recreate of one constraint instead of an `ALTER TYPE`), `registered_repos.index_strategy`, the all-or-none CHECK `ck_tasks_eval_columns_together` (`eval_run_id`, `instance_id` and `run_index` are all NULL or all set: the unique index below ignores rows with a NULL, so without it an enqueue that forgot `run_index` would silently lose its idempotency), and the partial unique index `uq_tasks_eval_instance_run` on `(eval_run_id, instance_id, run_index) WHERE eval_run_id IS NOT NULL`, which makes `enqueue` idempotent.
- **`patch_sha` stays a git sha** (the squashed commit when a PR was opened, else the scored commit at HEAD) and **the diff itself is in `patch_diff`**: a benchmark task that does not pass never pushes, so its commits die with the clone and the sha would point at nothing. `patch_diff` is NULL for a task that never reached the agent and `''` for one that did and changed nothing.
- **`score_reason`** is `Score.reason`, which `score()` computed and the pipeline used to discard; the report needs the sentence, and rescoring later is lossy (the `baseline_files` set that spares `django/test/client.py` is not stored). **For a benchmark task the pipeline's own text names no test id**: its log lines about the score carry counts only, and the "curated fail-to-pass test not red at baseline" reason says how many, not which. The agent reads neither, so this is hygiene for operator-side text that travels, not an oracle defence. Not covered, deliberately: `score()`'s own sentence for a failed attempt names up to three ids (a regression, a silenced failure, an expected test still red) and is stored as is, because the same ids are already in `task_test_runs` and in the instance file, and the report and gold validation show it to the maintainer.
- **`cost_usd` is NULL, not 0, when no priced call was made** (the stub and gold runners, a task that failed before the agent, calls that exist but none priced): "free" and "never priced" are different claims, and zeros would drag the benchmark's cost mean down for every gold and stub row. It equals the sum of the task's `llm_calls.cost_usd`.
- **`error_message` has exactly one meaning: `failed` = repolace itself broke.** An agent-caused stop (budget, step cap, no change, an LLM error, giving up) is `completed`, with the scorer's outcome and `agent_stop_reason` set, and `error_message` NULL. The reason is accounting: the report counts a `failed` task as a harness error, which the headline (`passed / planned`) still counts as a non-pass but the secondary `passed / admissible` figure *removes from its denominator*, so an agent-caused stop that raised `StageFailed` would quietly *improve* the secondary number and blur which failures were the agent's. A task with no scored attempt scores `failed` (not inadmissible: that word is for an instrument that failed, and this one worked).
- **The terminal write is conditional on `running`** (`finalize.write_terminal`, one function that takes every column as a required keyword, so a path cannot forget one): a late or duplicate writer finds the row already terminal and changes nothing instead of resurrecting a finished task, which is what Phase 2's at-least-once delivery needs. NUL is replaced before the write, because Postgres cannot store it and a failed write after the push and the PR would leave the row `running` with a pull request open; a minimal fallback `UPDATE` exists for a payload the database still refuses.
- **Every writer outside the pipeline is conditional on `running` too, and says who it is.** `interrupted: <ExceptionName>` is written by `run_task` itself when something that is not an `Exception` reaches it; the worker's bound arrives as `WorkerTimeout`, so a timed-out task reads `interrupted: WorkerTimeout` (a plain cancellation still reads `interrupted: CancelledError`). `worker: timeout` is the worker's backstop for a row `run_task` could not settle. `runner: abandoned` is the worker's reaper (stale heartbeat), `runner: interrupted` the eval runner's. The worker also refuses a row with `eval_run_id` set before claiming it, so a hand-published message cannot run a benchmark task outside the runner's manifest.
- **The task row is also checked against the scorer:** `_check_against_scorer` fails the task if the agent's reported attempts or last attempt disagree with what the scorer recorded, because a graph bug that dropped `last_attempt` would otherwise complete as FAILED "no scored attempt" inside the denominator with attempt rows sitting in the database.

### Task stages and heartbeat (migration 0014)

- **`task_stages`** has one row per pipeline stage a task entered (`instance`, `preflight`, `embedder`, `clone`, `index`, `retrieve`, `verify_baseline`, `record_baseline`, `baseline_files`, `branch`, `agent`, `review`, `squash`, `push`, `pr`, `finalize`): `started_at`, `ended_at`, `status` (`running`/`ok`/`failed`, behind a CHECK) and a short scrubbed `error`. It exists for the pipeline view (Phase 2 UI), which reads stage durations and the failing stage from it rather than from logs.
- **Stage rows are best-effort.** `run.py::_stage` writes them on short-lived sessions of their own and logs and drops any database error, so a blip can never fail a stage or replace its exception (same stance as `_best_effort_cost`). Consequence: a missing row, or one still `running` under a terminal task, means a lost write, not what the stage did. **The task row stays the source of truth** for status, outcome and error.
- **`tasks.heartbeat_at` and `tasks.claimed_by`** are set by the conditional `queued` -> `running` claim (`claimed_by` defaults to `<hostname>:<pid>`; a worker passes its own) and `heartbeat_at` is bumped every 30 s (`HEARTBEAT_INTERVAL_SECONDS`) by a background task inside `run_task`, which is cancelled and awaited in a `finally`. They are for the Phase 2 worker's reaper: a `running` row whose heartbeat is older than a few missed beats is a dead runner. A failed beat is logged and skipped, so a database blip cannot end a task.
- **The heartbeat only runs while the event loop does.** Checked: nothing in `run_task`'s path blocks the loop for long. The embedder load and warmup, the index pass (chunking, embedding, the sync `git` calls in `retrieval.index`), retrieval's query embedding and the workspace's tree removal all run in `asyncio.to_thread`, and git, docker and the sandbox are async subprocesses. The only synchronous work on the loop is small file reads (instance JSON, tool results). So a stale heartbeat does mean a dead or wedged process, but the reaper's stale threshold must still exceed the longest blocking call if one is ever added on the loop (or that call must move to a thread). The heartbeat's UPDATE is conditional on `status = running`, so a late beat cannot touch a finished row.

### Query indexes (migration 0015)

Indexes only: no column, no row changes. They exist because three query shapes read in proportion to history, not to the rows they return.

- **`ix_tasks_repo_created_id`** on `tasks (repo_id, created_at DESC, id DESC)` serves the keyset task list (`query_task_page` pages on `(created_at, id) < (:c, :i)`, newest first) and the estimate's repo window. All three columns after the equality column share one direction on purpose: Postgres turns a row comparison into an index condition only when they agree, and the old `(repo_id, created_at DESC)` index could bound `created_at` alone, leaving the tie-break to a filter. It **replaces** `ix_tasks_repo_id_created_at` (dropped): same columns, order and direction as a prefix, so every scan the old one served (the estimate, the enqueue's in-flight check, the cascade from `registered_repos`) is served by the new one, with one index write fewer per task insert. The gain shows when many rows share a `created_at` (an eval enqueue inserts a whole run in one statement, so every row gets the same `now()`); with unique timestamps the two differ by a couple of buffers.
- **`ix_tasks_active`** on `tasks (created_at, id) WHERE status IN ('queued', 'running')` is what the worker's sweeper and reaper (`tasks_recovery.running_with_stale_heartbeat`, `maintenance.sweep_queued`) read every minute; the live rows are a tiny, bounded share of the table whatever its age. `heartbeat_at` is deliberately **not** indexed: it changes every ~30 s per running task, and an indexed column would turn each beat into an index write and stop it being a heap-only update. The index applies when the planner sees the status value; Postgres plans a prepared statement with the values for its first executions and switches to a generic plan only if that is not costlier, and a generic plan could not use a partial index. Reasoned, not measured: if the sweeper or reaper is ever seen scanning `tasks` sequentially, look at that first.
- **`ix_llm_calls_task_created_desc`** on `llm_calls (task_id, created_at DESC)` removes the sort from the estimate's `DISTINCT ON (task_id) ... ORDER BY task_id, created_at DESC`. The ascending `ix_llm_calls_task_id_created_at` stays (the per-task cost sum and the relationship's `order_by` use it). **It does not bound that query:** the `DISTINCT ON` subquery still visits the latest call of every product task, so the `model` fallback costs time proportional to history on `llm_calls` even though it now summarises 30 tasks. Bounding the input would need a different shape (walk product tasks newest first and look up each one's latest call, stopping at 30) and a newest-first index over product tasks; neither is built.
- **Built with `CREATE INDEX CONCURRENTLY`** inside `autocommit_block()`, so `tasks` and `llm_calls` stay writable. That cannot be rolled back, and a cancelled concurrent build leaves an INVALID index that still owns its name, so every create is preceded by `DROP INDEX CONCURRENTLY IF EXISTS` and the old index is dropped `IF EXISTS`: running the revision again after a failure is safe (a test stamps back to 0014 over an invalidated index to prove it). The new list index is created before the old is dropped, and the downgrade recreates the old before dropping the new, so the list always has an index.
- **How it is checked** (`api/tests/test_api_query_plans_db.py`): the real statements are captured with `before_cursor_execute` while the real code runs, replayed under `EXPLAIN (FORMAT JSON)` with their real parameters on a few thousand seeded rows, with `enable_seqscan` off. That setting is deliberate: at that size the planner may rightly prefer a sequential scan, so the test asks whether an index *can* serve the query, and which one the plan then reads shows whether ours matches the filter and the `ORDER BY`. A reshaped query that stops matching its index fails there. The sweeper's query is mirrored in the test (the worker package is not importable from the API's tests); keep the two in step.
