# repolace — project context

This file is the persistent brief for any Claude Code session working on this repo. Read it before making architectural decisions — it captures the reasoning behind choices, not just the choices, so don't relitigate settled questions without a new reason.

## What this is

An autonomous software-engineering agent platform. A user registers a GitHub repo, repolace fetches its open issues, the user picks one issue and a target branch, and an agent pipeline (retrieve → plan → edit → test → review) attempts a fix, running in an isolated sandbox, and opens a PR on success. Previously named "Forge" — renamed to avoid collision with the well-known Minecraft modding tool and other existing projects.

**The core thesis:** most "AI coding agent" projects are common and unimpressive as a concept alone (SWE-agent, OpenHands, Aider, Devin all exist). The differentiation is in execution rigor that most hobby versions skip: a real benchmark with tracked success rate/cost/latency, production-grade reliability engineering (isolation, retries, observability), not just "it worked on my demo repo."

## Product scope (decided)

- User registers a repo (GitHub App install) → repolace indexes it (RAG) and fetches its issue list
- User picks one issue, specifies a target branch, enqueues a task
- Agent pipeline runs: retrieve relevant code → plan → edit → run tests → (loop back on failure, bounded retries) → review
- On success: PR opened against the specified branch
- **Merge conflicts:** if the target branch has moved and conflicts arise, a dedicated conflict-resolution agent (not a rerun of the Editor — reconciling two divergent intents is a distinct, harder problem) attempts a fix, looping until resolved or a retry cap is hit
- **Explicitly not before the MVP works:** PR conversation handling and the live workspace view. Both are wanted, both are recorded with their reasoning under "Later product visions", and neither is started until the core loop is verified and benchmarked.
- **Explicitly NOT repolace's job:** who can approve/merge a PR — that's GitHub's branch protection / required reviewers, not rebuilt here. repolace's own RBAC is scoped only to who can submit tasks and see cost/trace data.

## Architecture

Four-stage core loop, the hard/interesting part of the whole system:
1. **Retrieve** — repo-aware RAG (chunk repo into functions/classes, embed, retrieve relevant chunks for the issue) — necessary because full repos don't fit in context
2. **Plan** — Planner agent produces a change plan from the issue + retrieved code
3. **Edit** — Editor agent produces the actual diff
4. **Verify** — run the test suite in an isolated sandbox; on failure, a Debugger agent gets the failure output and revises, looping back to Edit (bounded retries)
5. **Review** — Reviewer agent sanity-checks the diff against the plan before PR

Agents are split by role (planner/editor/reviewer/debugger/conflict-resolver) rather than one large prompt, because a single agent conflating "what to do" with "doing it" gets unreliable with full repo + plan + edit context all at once. Splitting was deferred to Phase 2, after feeling where the Phase 1 single-agent version actually overloads.

**Why distributed-systems pieces are justified here** (not decoration — asked and answered explicitly during planning):
- **Isolated Docker sandboxes**: mandatory, not optional — this runs LLM-generated code, needs isolation regardless of scale, true even at N=1 concurrent task
- **Async job queue**: justified by task *duration* (a task can run minutes: clone, retrieve, plan, edit, test, retry), not by volume — needed so requests aren't held open and crashed workers don't lose in-flight tasks
- **LLM gateway**: real production concern (routing cheap vs. strong models per step, cost tracking) — not just an abstraction

## Tech stack

**Phase 1–4 (prebuilt tools; deliberate choice — de-risk product logic first, replace pieces later once real requirements are known from usage):**
- Orchestrator/API: Python, FastAPI
- Agent orchestration: LangGraph (already used at Accenture — planner/editor/reviewer/debugger map onto graph nodes with conditional edges for retry/conflict loops)
- Queue: RabbitMQ + Celery
- LLM gateway: LiteLLM (model routing + cost tracking)
- Vector store: pgvector (Postgres extension — repo-sized corpora don't need a dedicated vector DB; revisit only if deliberately demoing sharding under load)
- Embeddings: **local**, via `sentence-transformers` (`flax-sentence-embeddings/st-codesearch-distilroberta-base`, 768-dim) — deliberately *not* routed through the LLM gateway. Indexing embeds every chunk in a repo, so a per-call API price would make reindexing the dominant cost of the whole system and make benchmark runs expensive to repeat. A local code-tuned model is free, deterministic across runs (which the benchmark needs), and has no rate limit. Cost: it pulls torch (~2–3 GB) into any image that installs `rag/`. Revisit if the image size becomes the binding constraint, or if retrieval quality plateaus below what a hosted embedding model would give.
- DB: PostgreSQL (task/job/run state, issue metadata, cost/trace summaries)
- Sandbox execution: Docker, driven through the `docker` **CLI** (`verify/verify/backends/docker.py`), not the Python SDK: the argv *is* the security policy, so it is worth being a value the code can print, diff and assert on flag by flag rather than keyword arguments spread across an API call
- Observability: OpenTelemetry SDK → Grafana Tempo (traces) + Prometheus (metrics) + Loki (logs)
- Deploy: Docker Compose locally → Kubernetes (k3s locally, real cluster if needed) once the loop is stable; CI/CD via GitHub Actions

**Phase 5 replacement candidates** (highest payoff first, only after Phase 1–4 usage reveals real requirements):
1. Sandbox execution → custom Go implementation (isolation/lifecycle management fits existing systems-programming strength — see prior projects: a recursive DNS resolver, a BitTorrent peer-wire client, a bytecode VM)
2. LLM gateway → custom (once real routing/cost needs are known)
3. Queue → custom Redis-based (lower priority — Celery/RabbitMQ genuinely work well here; mainly a "prove you can" line, not a product improvement)
4. LangGraph → probably skip or last; least likely to actually beat the prebuilt tool for this fixed set of agent roles

**Repo structure (monorepo — justified: solo dev, tightly coupled services during active development, no reason to pay multirepo coordination overhead):**
```
repolace/
  api/            # FastAPI orchestrator
  worker/         # Celery worker (scaffolded; unused until Phase 2)
  agents/         # LangGraph graph, prompts, feedback filter, the nine tools
  gateway/        # LiteLLM wrapper: routing, budget, pricing, llm_calls recorder
  rag/            # AST chunking, embedding, pgvector indexing, hybrid retrieval
  shared/         # DB models, git workspace, GitHub client, instance format, path guards
  pipeline/       # run_task: the stages around the agent, gate, PR text, finalize
  verify/         # Sandbox backend, scoring, report parsing, hidden-test overlay
  infra/          # docker-compose.yml, k8s manifests (later)
  eval/           # SWE-bench-style benchmark harness (repolace-eval)
```

Dependency direction, which two review rounds enforced: `shared` ← `verify` ← `agents`, `shared` ← `gateway` ← `agents`, and `pipeline` → {`agents`, `gateway`, `rag`, `verify`, `shared`}. **`agents` must not import `rag`** (that is what keeps torch out of agent tests; `agents/pyproject.toml` does not list it). `agents` does import `verify.scoring`, which loads SQLAlchemy and pgvector through `shared`'s models, but not torch or LiteLLM.

**Indexing is Python-only for Phase 1 — deliberate, with multi-language support planned later.** The chunker uses `tree-sitter-python` and Python node types (`function_definition`, `class_definition`, `decorated_definition`), and `find_python_files` matches `*.py`. A repo in any other language indexes to zero chunks and retrieval returns nothing. Two consequences to hold onto:

- **The Phase 1 benchmark repos must be Python.** A non-Python issue in the 15–20 hand-picked set would score as a failure for reasons that have nothing to do with the agent.
- The empty-index case is logged (`rag.index.no_python_files`) rather than passing silently, since zero chunks otherwise looks exactly like a successful index.

Extending is a contained change, not a rewrite: add the grammar package, and map that language's node types onto the same function/method/class-skeleton/module shape the chunker already emits. The storage, embedding, retrieval and RRF layers are language-agnostic already.

`rag/` is a separate workspace package from `shared/` (not nested inside it) so RAG-specific dependencies (tree-sitter, embedding client) don't leak into every service that imports `shared/` — same reasoning as why `gateway/` is its own package rather than living in `shared/`.

**Amendment (the one exception):** `shared/` depends on `pgvector`. The `CodeChunk` ORM model has to live in `shared/repolace_shared/db/models.py` with every other table, because Alembic autogenerate works off a single `Base.metadata` — splitting models across packages means either a second migration chain or an import graph where `shared` reaches into `rag`. `pgvector` is a thin SQLAlchemy type adapter (its only dependency is numpy), so the leak is small and bounded. The rule still holds for what actually matters: tree-sitter and sentence-transformers/torch stay in `rag/` and never reach services that only import `shared/`.

**Package naming:** every workspace package uses a distinct top-level import name (`repolace_api`, `repolace_worker`, `repolace_agents`, `repolace_gateway`, `repolace_shared`, `repolace_pipeline`, `retrieval`, `verify`, `harness`). They previously all used `app`, which silently broke both the API and the worker under `uv sync --all-packages` — editable installs append each package root to `sys.path`, so four `app/` directories shadowed each other in .pth order. Do not reintroduce a shared top-level name.

**Note:** `uv sync` alone prunes workspace members, because the root package declares no dependencies. Use `uv sync --all-packages`.

## Logging / observability timing (decided explicitly — don't relitigate)

- **Phase 1**: structured JSON logging with a task ID on every log line, from day one. Cheap now, expensive to retrofit across every agent call later.
- **Phase 3**: full OpenTelemetry instrumentation (one task = one trace, each pipeline stage = a span with timing/cost/status) + Grafana stack. Deliberately *not* done in Phase 1 — at MVP scale (synchronous, one sandbox, no queue) there's no concurrent complexity yet for a trace to meaningfully stitch together. Tracing earns its cost once Phase 2's async queue/workers introduce real concurrency.

## Build phases

**Phase 0 — Scaffolding (~15–20h)**
Monorepo setup, Docker Compose (Postgres + Redis + RabbitMQ), FastAPI skeleton, GitHub App install for repo registration + issue fetching. No agent logic yet. The `worker` service (Celery, broker=RabbitMQ, result backend=Redis) is also stood up in Phase 0 — ahead of when Phase 1 actually needs it, since Phase 1's pipeline runs as a host process per task, not through a queue (see below); the worker container sits unused until Phase 2 wires real task dispatch through it.

**Phase 1 — MVP: single-agent loop (~100–120h) — the resume-worthy checkpoint**
- One repo, repo-aware RAG (pgvector)
- Single agent (not yet split by role) doing plan → edit → run tests → retry on failure, via LangGraph, bounded retries
- **The LiteLLM gateway goes in from the start, not in Phase 2** (moved deliberately — do not move it back). Every model call is routed through `gateway/` on the agent's first run, so cost per task is recorded from the first benchmark run rather than retrofitted. The benchmark's headline is "success rate, cost and latency"; cost that starts being measured halfway through the instance set is not comparable across the set, and the earlier runs cannot be re-priced without re-running them — the same argument as `task_test_runs` storing raw sets. The cost of pulling it forward is an abstraction over one provider before the routing requirements are known, which is small and reversible; the cost of deferring it is an unrepeatable measurement, which is not.
- Verify: the repo's suite runs in a rootless locked-down container from a prepared per-repo image, against a source tree exported without `.git`, once at the base commit and once after the edit — and the two runs are scored into `tasks.outcome` (see "Verify sandbox"). Pulled forward from Phase 2, where this bullet used to live: the success criteria are unfalsifiable without a baseline, so a Phase 1 that opens PRs it cannot score has no benchmark to report.
- **One host process per task, no queue.** `POST /repos/{id}/tasks` only inserts a `queued` row; `repolace-run-task <task_id>` (`pipeline/repolace_pipeline/cli.py`) claims it and runs `run_task` to completion in its own process, on the host, against the containerised Postgres. (An earlier revision of this section said "inline in the API process". The code does not do that: the CLI process is what keeps torch and the retrieval stack out of the API image.) The benchmark runner starts K such processes at a time, which is concurrency without a queue. The Phase 0 worker/RabbitMQ/Redis containers exist but are not used for pipeline execution.
  **What Phase 2 changes:** a Celery worker calls the same `run_task` with a long-lived engine, GitHub client and sandbox backend instead of the CLI's per-process ones (that is why `run_task` owns none of them), the process-per-task isolation goes away, and the claim guard (`queued` → `running` is conditional) becomes load-bearing because a queue delivers at-least-once.
- Opens a real PR on success
- Structured JSON logging with task IDs (see above)
- Benchmark: 15–20 hand-picked real GitHub issues, tracked pass/fail, cost, latency
- Target claim: "autonomous agent takes a GitHub issue, retrieves relevant code, patches it, verifies via test suite, opens a PR — benchmarked at X% on N real issues"

**Phase 2 — Real product (~60–80h)**
- Split into specialized agents (planner/editor/reviewer/debugger)
- Async queue (RabbitMQ/Celery), worker pool
- Merge-conflict resolution sub-loop (own agent role, bounded retries)
- UI: task list with status badges, enqueue flow (issue → branch → confirm), pipeline view (log-backed, not full traces yet)

**Phase 3 — Observability and testing rigor (~55–70h)**
- Full OpenTelemetry instrumentation + Grafana stack (Tempo/Prometheus/Loki)
- Pipeline-trace UI switches from log-based to real spans
- Full test suite: unit, integration, E2E through the whole pipeline. **Database-backed tests specifically**: the one defect that reached a real run (a `MissingGreenlet` from reading an ORM attribute after `rollback()` expired it) was in a DB path with no coverage, while 148 passing tests touched no database
- Expand and track the benchmark over time

**Phase 4 — Deployment / hardening (~40–50h)**
- Kubernetes + CI/CD (GitHub Actions)
- RBAC scoped to task submission + dashboard access only (not PR approval)
- Failure-path polish: what a user sees on failure, retry/resume semantics if a worker dies mid-task

**Phase 5 — Replace prebuilt pieces (open-ended)**
See replacement order above.

**Rough totals:** Phase 0–1 ≈ 115–140h → 8–15 weeks at 9–15h/week. Phases 2–4 add ≈155–200h more. Phase 5 is ongoing.

## Later product visions (not before the MVP is solid)

Two directions the product should grow in, recorded now because the reasoning is
worth keeping, and explicitly **not** scheduled before the core loop works end
to end and has a benchmark number behind it. Think Phase 4-ish, after Verify,
the real agent and the eval harness exist. The risk they carry is not technical
difficulty — it is that both are more fun to build than the MVP, and building
them first would produce an impressive demo sitting on an unverified pipeline.

### PR conversation handling

When a human mentions the app in a comment on a PR repolace opened, the agent reads the comment in the context of that PR's diff, decides what it calls for, and responds.

**Acting is optional, and deciding not to act is a first-class outcome.** "LGTM" needs a reaction, not a commit. So the first step is classification — roughly: *needs a code change* / *needs an answer only* / *needs nothing*. Getting this wrong in the eager direction is worse than the cautious direction: an unnecessary commit on someone's PR is noisy and erodes trust, while a missed nudge just gets repeated.

This is a **different task shape from "fix an issue"**, and the existing model does not express it:

- The branch and the PR already exist, so there is no clone-branch-push-open sequence — it is clone, checkout the *existing* agent branch, amend, push to it.
- `Task` is keyed to an `issue_number` with a `target_branch`. A follow-up task is keyed to a PR and a comment. Either `Task` grows a kind discriminator, or this gets its own table.
- The task terminates by *replying*, which may or may not involve a commit. `TaskStatus` has no state for that.
- Squash-to-one-commit is wrong here. The PR already has a clean commit; a follow-up should add a further commit so reviewers can see what changed since their comment, not silently rewrite what they already reviewed.

**Infrastructure it needs that does not exist:** the webhook handler currently processes only `installation` and `installation_repositories`. This needs `issue_comment` and `pull_request_review_comment`, plus the ability to post a reply — and the App must be able to see and write comments.

**The security consideration, which is new and real: comment text is untrusted input that reaches an LLM prompt.** Anyone who can comment on a public PR can attempt prompt injection — "ignore your instructions and push to main", or instructions to exfiltrate. Unlike an issue body, which the repo owner controls, a PR comment can come from anyone on the internet. Treat comment text as data, never as instruction: the agent's authority must come from its own system prompt and be bounded by what the pipeline permits (it can commit to *this* agent branch and reply to *this* thread, and nothing else), not from anything the comment says. Worth deciding before this ships, not after.

### Live workspace view

While a task runs, the user can open a browser-based editor attached to the checkout the agent is working in — watching files change as the agent edits, browsing the code, reading the diff as it forms.

**Read-only, with a chat box.** The viewer cannot edit files. If they want something changed they say so in a chat panel beside the code, Copilot-style, and the agent picks it up and works on it. This is a better design than an editable tree, not a lesser one: it removes concurrent writes entirely, so the "index before any edit" ordering rule and the per-attempt commit checkpoints both keep holding, while the interactivity that made the feature attractive survives intact.

**Where it runs is the whole design question, and the sandbox decision above answers it: inside the sandbox.** A browser editor includes a terminal, so hosting it on the worker would hand any viewer arbitrary code execution on the host with the App's credentials in its environment — reintroducing, deliberately, the exact exposure the sandbox exists to prevent. Inside the sandbox the terminal is contained by construction, and the sandbox already holds the source files. It fits the boundary rather than fighting it.

Consequences to hold onto:

- **It stretches the sandbox's lifetime.** Verify wants a short-lived container per attempt; a live view wants one that persists for the task and is reachable from a browser. Those are reconcilable — a long-lived viewing container alongside short-lived test containers, sharing the file copy — but it is a real change to "start a fresh container per run".
- **It needs network reachability into the sandbox**, which is otherwise deliberately network-off. Ingress is not egress, but it is a new surface and wants authentication in front of it.
- **The clone is ephemeral and deleted when the task ends** (see "Checkout lifecycle"), so the view dies with the task. That is probably correct — the PR is the durable artifact — but it means "let me look at what it did" only works *during* the run, which is worth being explicit about in the UI.
- **Access control is the gap.** RBAC is deferred to Phase 4 and currently scoped to task submission and dashboard access. A live editor with a shell needs an answer to "who can open this" *before* it ships, not after.
- **A steered task is not an autonomous result, and the benchmark must say so.** If a human can redirect the agent mid-run, a task where that happened is a different kind of evidence from one where it did not. Decided: record the number of human turns on the task and **exclude any task with human turns from the headline figure**, reporting "passed autonomously" and "passed with human steering" as two separate numbers. Same discipline as `passed_with_test_edit` — the exception is tracked, never quietly folded in. The column arrives with the feature; building it before the chat exists would be speculative schema.
- **A live chat needs a task to talk to.** Today a task is a one-shot CLI process that runs to completion. Interactive steering needs a persistent, addressable task with a bidirectional channel — which is a real architectural change, not a UI feature, and another reason this waits for the queue and worker pool.

Sequencing: this is naturally a Phase 3 feature — it wants the sandbox (Phase 2/3), the trace UI, and Phase 4's RBAC pulled forward. It is also the single most demo-able thing on this list.

## UI (mocked, not yet built)

- Task list per repo: rows with git-flavored status badges (`queued`/`running`/`pr_opened`/`completed`/`conflicting`/`failed`) — keep this vocabulary equal to the DB `TaskStatus` enum, which has exactly these six. `completed` means the pipeline ran to the end and opened no PR (read `outcome` and `agent_stop_reason` for why); `failed` is reserved for "repolace itself broke" and is the only status that sets `error_message`. `conflicting` is in the enum and nothing sets it: the conflict-resolution loop is Phase 2. **`merged` was replaced by `pr_opened`**: a task's work ends when the PR exists, and whether it later merges is decided by branch protection and human reviewers — explicitly not repolace's job. Nothing subscribes to PR webhooks, so `merged` was a state the pipeline could never reach. Add it back only alongside the webhook that could actually set it.
- Status is not outcome. A row can show `pr_opened` and still have scored `failed` — status is where the pipeline got to, outcome is whether the issue was fixed. The task list should show both, or it will overstate success.
- Enqueue flow: pick issue → pick target branch → confirm screen (shows PR target branch + a real computed cost estimate, not a static placeholder) → start
- Pipeline trace view: horizontal stage strip (Retrieve/Plan/Edit/Test/Review) with per-stage status color and duration — in Phase 2 this is backed by logs; in Phase 3 it's backed by real OTel spans

## Index freshness protocol (decided)

When a task starts work on an issue:

1. Read the repo's last indexed commit (`registered_repos.indexed_commit_sha`).
2. If it equals the checkout's current commit, the index is current — use it as is.
3. Otherwise index incrementally from that commit: `git diff <indexed_sha> <current_sha>`, then delete and re-chunk **only** the files that changed. Untouched files keep their existing chunks and embeddings.

Implemented in `rag/retrieval/index.py::reindex_if_stale`, single-flight per repo via a transaction-scoped advisory lock.

## Checkout lifecycle (decided)

**One ephemeral clone per task. No persistent clone cache.**

At the start of a task: clone the repo to a temp directory, index from it, let the agents work in it, and delete it when the task ends. Nothing is kept between tasks.

Why this works despite incremental indexing needing the previously-indexed commit: **chunks and embeddings live in Postgres, not in the checkout.** Throwing the tree away does not throw the index away, so re-cloning still skips re-embedding every unchanged file — which is the expensive part. And a *full* clone contains complete history, so `git diff <indexed_sha> <current_sha>` resolves in a brand-new clone. Persistence would only save download time, not correctness.

The one hard constraint: **the clone must not be shallow.** `--depth 1` cannot resolve the previously-indexed commit, so every index would silently degrade to a full reindex and `indexed_commit_sha` would never save any work. If clone cost becomes a problem on large repos, the thing to reach for is a partial clone (`--filter=blob:none`, paired with `--no-renames` on the diff so rename detection does not pull blobs back down): full commit history, deferred file contents. Measure before adopting — untested here.

**Ordering within a task matters.** Index first, from the clean checkout, *before* any agent edits it. Otherwise a reindex would capture the agent's own uncommitted work as if it were repo state and write it into the index.

Because each task gets its own clone, two concurrent tasks on one repo are isolated at the filesystem level for free. The advisory lock in `reindex_if_stale` is still needed — it protects the shared `code_chunks` rows in Postgres, which separate checkouts do not.

When the previously-indexed commit is genuinely unreachable — force-push, or an upstream `gc` — `reindex_if_stale` catches the failed diff and falls back to a full reindex rather than erroring permanently.

**Settled since (this was "still open"):** Verify runs against a copy, never the checkout. Verify executes LLM-generated code and the repo's own test suite, either of which can mutate or delete files, and the copy is what omits `.git` (see "Byte-identical export" under "Verify sandbox"). The checkout also no longer contains the installation token (see the branch/PR section below).

Implemented in `shared/repolace_shared/git/workspace.py::task_workspace`, an async context manager that clones into a temp directory and deletes it on exit. Cleanup failures are logged, never raised: losing a temp directory is a disk leak worth seeing, but it must not replace the exception explaining why the task failed. Expect that path to get exercised once the sandbox runs as root and leaves files the worker cannot delete.

## Branch and PR flow within a task (decided)

Inside the per-task clone:

1. **Clone** at the target branch; this is the base commit.
2. **Index** from the clean tree (before any edits — see above).
3. **Baseline test run** at the base commit, recording the pass/fail set the success criteria compare against.
4. **`git checkout -b`** an agent branch. Plain branch, not a worktree: a worktree exists to share one object store across several trees, which the persistent-cache design needed and this one does not.
5. **Agent works on that branch, committing each edit attempt.** The commits are checkpoints, not history for humans — they let the Debugger `git reset` back to a prior attempt instead of trying to un-edit a bad state, and give the trace UI a per-attempt diff.
6. **Verify** on the branch; loop back to Edit on failure, bounded retries.
7. **Review** the branch against the base: `git diff <base>...<agent-branch>` is exactly what the Reviewer reads and what the PR will show.
8. **Squash** to a single clean commit, so the PR is not "attempt 1, attempt 2, fix debug output".
9. **Push the branch to the remote and open the PR** against the target branch.
10. **Delete the clone.**

**As built in Phase 1 (what differs from the list above, and why).** Steps 5-7 changed shape when the agent became a single tool-loop agent rather than planner/editor/debugger roles. There are two kinds of commit on the agent branch. A *scored attempt* is made by `AttemptScorer.verify_attempt` (`pipeline/repolace_pipeline/attempts.py`): it commits the tree, runs the scored suite, records the `task_test_runs` row. A *checkpoint* is made by the `run_python` and `run_tests` tools before they hand the tree to the sandbox, because the export refuses a tree that differs from HEAD; checkpoints are never scored. So HEAD can be ahead of the last scored attempt, and **`AgentResult.last_attempt` is the only scored state**: before reading the diff, squashing or pushing, the pipeline `rewind_to(last_attempt.commit_sha)` whenever HEAD differs (or to the base commit if nothing was scored). Otherwise the PR would carry edits no suite ever ran against, under a verdict that belongs to an earlier commit. Step 7 is `review_diff()` feeding `tasks.patch_diff` and the PR body; there is no Reviewer agent in Phase 1. Step 3 can also end the task early: an unusable baseline, or a curated fail-to-pass test that was not red at the base commit, completes the task as inadmissible *without running the agent* (an agent run against an unscoreable instance would burn its budget for a result that is thrown away). The exception is a baseline that never reached the container runtime (`SandboxUnavailable`): that is repolace's failure, not the instance's, so the task is `failed` (the baseline row is still recorded). Before this was split out, a dead daemon completed the task as inadmissible, and gold validation drops an instance on exactly that.

**Step 9 is the part that is easy to overlook:** the branch has to exist on GitHub for a PR to reference it, so it must be pushed before the temp directory is discarded. That requires the App installation to hold `contents: write`. Installation tokens expire after an hour and a retry loop can outlive one, so the token must be refreshed immediately before the push rather than minted once at task start and assumed valid.

**Correction to an earlier revision of this note (matters, don't undo it):** it said the clone remote should carry the installation token as `https://x-access-token:<token>@github.com/...`. **Do not do that.** Git writes the remote URL into the checkout's `.git/config`, and step 6 runs LLM-generated code against that same checkout. An agent that reads `.git/config` would be holding a live token with `contents: write` on *every repo the App is installed on* — the blast radius is the whole installation, not this one task.

The token therefore never touches the checkout and never appears in `argv` either. Instead every git invocation carries a per-command credential helper, `git -c credential.helper='!f() { ... }'`, which echoes the token from an environment variable the subprocess is given. `-c` does not persist into the cloned repo's config, so the stored remote stays the plain unauthenticated URL. The preceding `-c credential.helper=` clears any inherited global helper first, so a developer's keychain cannot answer with a different account.

### The part that keeping the token out of the tree does *not* fix

Security review of the implementation found the above is necessary but nowhere near sufficient, and the gap is worth stating plainly because it is easy to feel finished after solving the first half. **The token is not in the checkout, but the checkout still controls where the token is sent and what code the host runs.** `.git` lives inside the tree the sandbox writes to, and git treats parts of `.git` as executable configuration.

Two concrete failures, both demonstrated against this code:

1. **Credential exfiltration.** `push` resolves `origin` from `.git/config`. Verify can rewrite `remote.origin.url`, or add a `url.<evil>.insteadOf` rule (which rewrites *explicit* URLs too, so passing a URL instead of a remote name is not a fix), or set `http.proxy`. A credential helper that answers whatever it is asked then hands the installation token to an arbitrary host over plain HTTP. **Fixed:** the helper now parses git's stdin and releases the token only for `protocol=https` + the expected host, which is held in `GitRepo.credential_host` rather than read from the checkout. A rewritten remote now produces a failed push instead of a stolen token.
2. **Host code execution.** `.git/hooks/post-commit`, `post-checkout` and `pre-push` all fire on the host during steps 5, 4 and 9; `core.fsmonitor` fires on every `status`; a `.gitattributes` `diff=X` paired with `diff.X.textconv` fires during the Reviewer's diff. `--no-verify` covers `pre-commit`/`commit-msg` only. **Partly fixed:** `core.hooksPath=/dev/null` and `core.fsmonitor=` are now in the base args; git's environment is built from an allowlist so the App private key and database URL are no longer inherited by git or anything it spawns; and its config files are pinned to `/dev/null`, so no `~/.gitconfig` or `/etc/gitconfig` is read (see the correction under "Danger 2" — a tracked `.gitattributes` plus the operator's own config was a live route that none of the base args covered). `retrieval.index` carries the same pins and the same allowlist via `UNTRUSTED_TREE_CONFIG_ARGS`/`sanitized_git_env`; it remains a **separate** git wrapper from `repo.py`'s, which is a known duplication and a deliberate deferral, not an oversight.

**The second one is not properly closed, and should not be treated as closed.** Enumerating dangerous config keys is a losing game — `filter.*.smudge`, `core.pager`, `core.sshCommand`, `uploadpack.packObjectsHook` are all the same shape. The durable fix is architectural: **do not run git on the host against a `.git` the sandbox could write to.** Either restore `.git/config` and `.git/hooks` from a trusted copy after Verify, or have Verify emit a patch that gets applied in a clean clone. **Decide this together with the sandbox isolation mechanism — it is the same decision, and it also settles the "Verify in the checkout or a copy" question above.** (That decision has since been made: the sandbox receives a byte-identical export without `.git` and never writes back into the checkout. See "Danger 2" and "Byte-identical export" under "Verify sandbox".)

A note on the `argv` reasoning: keeping the token out of `argv` defends against *other users* on the host, since `/proc/<pid>/environ` is `0400` while `argv` is world-readable. It does **not** defend against root or a same-UID process. If the sandbox runs as root and shares a PID namespace, it can read the token out of the worker's environment for the duration of a clone or push regardless.

Three more things that only show up once this is real code, all now covered by tests:

- **The clone must not be shallow *or* single-branch,** and that has to be asserted, not assumed. Either flag drops the previously-indexed commit, `git diff <indexed_sha> <current_sha>` fails, and every task silently falls back to a full reindex — a cost regression that never surfaces as an error. `clone()` fails loudly if the result is shallow.
- **Killing a timed-out git means killing its process *group*,** not the `git` process, and the pgid must be captured at spawn rather than looked up at kill time. Git delegates to helpers (`git-remote-https`, and the credential helper above, which is a shell). Kill only the parent and those children keep the stdout pipe open. That strands the command two different ways: if git has not been reaped, `Process.wait()` blocks because the transport needs every pipe closed; if git *has* been reaped, `wait()` returns instantly off the recorded exit code — and `os.getpgid()` then raises, so the fallback does nothing and the orphan leaks while the timing looks perfect. Spawned with `start_new_session=True` (so pgid == pid), killed with `killpg` on the cached value.
- **Squash builds the commit before moving the branch.** The obvious `reset --soft <base>` then `commit` moves the ref first, so any failure in between strands the branch at base with every attempt commit unreachable — in a clone that is about to be deleted, at step 8, after all the work succeeded. This is reachable by ordinary means: after Verify runs a test suite the tree is full of untracked artifacts, so a net-zero branch passes a `status --porcelain` guard (which counts untracked files) and then fails `git commit` (which does not). Now: compare `HEAD^{tree}` against `<base>^{tree}` first, then `commit-tree`, then move the ref onto a commit that already exists.

**Related, and now closed:** `commit_all` stages with `git add -A`, so artifacts a test run leaves behind (`.pytest_cache`, `__pycache__`, coverage files) would get swept into the next attempt commit and into the PR diff for any repo whose `.gitignore` does not cover them. Verify runs against `export_tree`'s copy, which is a sibling of the checkout rather than inside it, so the suite never writes into the tree `git add -A` sees. Keep it that way: moving the export inside the checkout would reopen this silently, and the symptom would be a dirty PR rather than an error.

If the target branch moved while the task ran, the PR conflicts — this is where the conflict-resolution agent comes in. The per-task clone keeps that window small but not zero.

Implemented in `shared/repolace_shared/git/`: `repo.py` (the git CLI wrapper) and `workspace.py` (`task_workspace`, whose methods are steps 1 and 4–10 in order). Steps 2, 3 and 6 belong to the caller — indexing and the Verify sandbox respectively.

## Verify sandbox (decided)

Verify runs the target repo's test suite twice per task — once at the base commit for the baseline, once after each patch attempt. That means executing arbitrary code from two sources: the model's patch, and **the repo's own test files**. The second is the sharper one: `pytest` executes `conftest.py` at *collection*, before any test runs and before a patch is even involved. Registering a hostile repo is the whole attack; no agent cooperation is required.

There are **two independent dangers here, and a sandbox only addresses one of them.** Conflating them is the mistake to avoid.

### Danger 1 — untrusted code running (containment)

Handled by the sandbox. The naive shortcut, mounting the host's `/var/run/docker.sock` so the worker can spawn sibling containers, is root-equivalent on the host and defeats the entire point.

**Decided: right-size the isolation to who can register a repo.** Today that is one person hand-picking 15–20 benchmark repos, so the attacker would have to be the operator. A locked-down rootless container is proportionate: no network during the test run, dropped capabilities, `no-new-privileges`, read-only root filesystem, memory/CPU/PID caps, and a hard timeout. Escalate to gVisor (syscall interception) or Kata/Firecracker (real VM per sandbox) **when strangers can register repos, not before** — gVisor has syscall-compatibility gaps, Kata needs nested virtualisation, and Firecracker is a build project rather than a drop-in runtime. Keeping the boundary clean is what makes the runtime swappable later.

Note a container is **not** a VM: it shares the host kernel, so a container escape is usually a kernel bug. That is precisely the gap gVisor and Firecracker exist to fill, and the reason the escalation path above is worth keeping open.

### Danger 2 — the confused deputy (`.git` is executable configuration)

**A better sandbox does not fix this, at any price.** Nothing escapes. The sandbox writes a file, stays perfectly contained, and exits. Then the *host*, later, voluntarily reads that file and acts on it.

Both halves were reproduced against this codebase:

- **Host code execution.** The sandbox writes `.git/hooks/post-commit`. The container is torn down. The host then runs an ordinary `git commit --no-verify` for the next attempt — and the hook executes as the worker user. Verified: `--no-verify` suppresses `pre-commit` but **not** `post-commit`. `post-checkout` fires on `git checkout -b`, `pre-push` on the push, and `core.fsmonitor` on *every* `git status`.
- **Credential redirection.** The sandbox rewrites `remote.origin.url` in `.git/config` (or adds `url.<evil>.insteadOf`, which rewrites explicit URLs too, so passing a URL instead of a remote name is not a fix; or sets `http.proxy`). The host's next `git push` then sends the installation token to a host of the attacker's choosing. Demonstrated against a local listener, which received `x-access-token:<token>` in cleartext over plain HTTP.

Hooks are **not** shippable in a repo — `git clone` never transfers them, verified. Both attacks require the sandbox to *write* into `.git`, which is only possible because `.git` happens to sit inside the working tree the sandbox legitimately needs.

**Correction to an earlier revision of this note (matters, don't undo it):** the sentence above says both attacks "require the sandbox to *write* into `.git`". That is true of those two instances and **false of the class**, and the gap was reproduced against this code. `.gitattributes` is a **tracked file** — an ordinary file in the repository, present in every clone, which the sandbox never has to touch. It supplies the *selector* half; the *command* half comes from the operator's own `~/.gitconfig`. `*.py filter=x` plus a global `filter.x.smudge` runs a command on the host during any checkout; `diff=x` plus a global `diff.x.textconv` runs one during the Reviewer's diff. `_BASE_ARGS` stops neither — it clears the keys it enumerates, which is the enumeration game this section already calls unwinnable — and withholding `.git` from the sandbox stops neither, because neither half came from the sandbox.

**Fixed, structurally:** git's environment now pins `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` to `/dev/null` (`sanitized_git_env`), so git reads **no configuration file it was not handed on the command line**. No key list, so keys nobody has thought of yet are covered. Note `HOME` cannot simply be dropped from the allowlist instead — git needs it for other reasons, and the suite itself had been silently running against whatever the developer had configured until this landed.

This does **not** cover the checkout's own `.git/config`, which the sandbox *can* write. That half is closed separately, by never letting a filter or attribute run during the export at all — see "Byte-identical export" below.

**The lesson worth carrying:** *"the sandbox never receives `.git`" bounds what the sandbox can plant, not what the host will read.* Every host-side git invocation is still a confused deputy for whatever configuration the host itself supplies.

### A third route into the same class: paths the host chooses to follow

`.git` sitting outside the sandbox does not help when the *host* is handed a path and follows it. Two routes were live and are now closed, and neither involves the sandbox or `.git` at all:

- **Arbitrary host file read.** `retrieval.index` walked the checkout with `os.walk` and read any `.py` it found. `os.walk` does not descend a symlinked *directory*, but it does list a symlinked *file*, and `read_text` resolves it. git stores a symlink as an ordinary mode-`120000` entry and clones it back verbatim, so a repo committing `settings.py -> /home/worker/.env` put a host file into `code_chunks.content` — from where it is retrievable and, in Phase 2, goes into an LLM prompt at a third-party API. Reproduced. Note the *incremental* path is the live one and never went through the walk at all: `_incremental_index` builds `repo_path / rel` straight from `git diff --name-only`.
- **Arbitrary host file write.** `apply_stub_edit` did `repo_path / file_path`. Under pathlib semantics that discards `repo_path` entirely for an absolute `file_path` — `Path("/repo") / "/etc/cron.d/x"` *is* `/etc/cron.d/x`, with no `..` and nothing in the string that looks wrong — and follows a symlink for a relative one.

**The rule now: every path that reaches the filesystem from a database row, a diff, or a model goes through `repolace_shared.paths.resolve_within`, and a symlink is refused rather than followed.** Refusing rather than following matters even when the target happens to land inside the tree: following it would still be letting the repository choose where a later read or write goes.

The Editor additionally refuses anything under `.git`. That is protection the *stub* editor does not need — its path came from a row it wrote itself — and the real Editor will: `.git/hooks/post-commit` is one model-chosen string away from host code execution on the next `record_attempt`. Deliberate, and worth keeping when the stub is replaced.

**Decided: the sandbox never receives `.git`.**

- **In:** source files only, copied out of the checkout without `.git`. No credentials, no remote, no network during the test run.
- **Out:** *data only* — the pass/fail test-ID sets and stdout. Never files that get executed, never anything written back into `.git`. Returning, say, a patch file that the host blindly applied would reopen a smaller version of the same hole.

This deletes the whole class rather than blocking instances, which matters because the instance list (`diff.<d>.textconv`, `filter.<d>.smudge`, `core.pager`, `core.sshCommand`, `uploadpack.packObjectsHook`, …) grows with every git release. The mitigations already in `_BASE_ARGS` (`core.hooksPath=/dev/null`, `core.fsmonitor=`) and the host-checked credential helper stay as defence in depth — two independent things then have to be wrong — but they are no longer the primary control.

This also settles the older open question of **whether Verify runs in the checkout or a copy: a copy, necessarily**, since the copy is what omits `.git`.

### Byte-identical export (decided)

The sandbox receives the tracked tree, and it now receives it as **the bytes the commit contains**: enumerated with `git ls-files -s -z`, fetched with `git cat-file --batch`, written straight to disk. Not by asking git to materialise a working tree, because every mechanism that does applies some transformation, and each transformation is a way for what the sandbox runs to differ from what the commit holds and the Reviewer reads.

- **Not `git archive`**, for the reason already recorded: it honours `export-ignore` in `.gitattributes`, which would let a repository hide its own test files from the run that establishes ground truth. An attack on the benchmark number, and the kind that would never look like an attack.
- **Not `checkout-index`**, which was the previous implementation. It honours neither `export-ignore` nor `export-subst` — but it *does* run clean/smudge filters, `text`/`eol` conversion and `ident` expansion. Measured on this repository with a one-line `.gitattributes` (`*.py text eol=crlf`): **72 of 110 tracked files came out byte-different from the commit.** A `filter` driver is worse still, since its value is an arbitrary command run on the host. Pinning git's config files (see the correction under "Danger 2") closed the half of that which came from the operator's `~/.gitconfig`; it does **not** close the checkout's own `.git/config`, which is inside the tree the sandbox writes to. Reading blobs consults no attribute or filter machinery at all, so it closes both — structurally, with no key list.

Only index entries are listed, so `.git`, untracked files and ignored build artifacts are excluded by construction, exactly as before.

**Modes `120000` (symlink) and `160000` (gitlink) are refused loudly**, not approximated. A submodule has no blob to write, and `checkout-index` silently left an empty directory — so the suite ran against missing sources and produced a confidently wrong number rather than an error. A symlink is not a file with content, so "the bytes match the commit" stops being a well-formed claim, and materialising one would put a path resolving outside the export into a tree the host later deletes. Paths stay `bytes` end to end for the same fidelity reason: a repository may hold a filename that is not valid UTF-8, and decoding it with `errors="replace"` would write a *different* file.

**The cost is real and accepted:** a repository containing any symlink cannot currently be exported — and this repository is one of them, since `infra/.env` is a tracked symlink. Some real Python projects have a `LICENSE` or docs symlink too. The refusal names every offender at once so a rejected benchmark repo is diagnosable at a glance, and it raises a distinct `GitExportError`, so a future `RepoSpec` opt-in is a contained addition rather than a rewrite. **This is a constraint on picking benchmark repos, and it should be checked before the set is finalised, not after.**

**Directory modes go all the way down, not just onto the root.** `mkdir`'s mode argument is masked by the process umask, and the old code chmodded only the export root — so `checkout-index` created `0755` subdirectories under a `0777` root, and a sandbox running as an unprivileged uid got `EACCES` writing a `__pycache__` beside its own code. That surfaces as an unscoreable run, which silently drops the instance from the benchmark rather than failing visibly. Files keep `0644`/`0755` from their index mode: what the sandbox needs is permission to create entries *in a directory*, and the executable bit has to survive for suites that shell out to a tracked script.

**`tree_matches_head` gates all of this, and is a precondition rather than a warning.** It compares the index *and* the working tree against HEAD. It previously passed `diff-index --cached`, which compares only the index and **ignores the working tree** — and the agent edits the working tree directly, with staging happening later in `record_attempt`. So an unstaged edit passed the guard, the export handed over HEAD's content, the sandbox tested code the agent had not written, and the pass/fail sets were attributed to the attempt regardless. A confidently wrong measurement, which is the worst shape this stage can fail in. It now uses `status --porcelain --untracked-files=no`: that refreshes the index itself, so stat noise cannot read as a modification, and it needs no exit-code interpretation — `diff-index --quiet` exits 1 for "differs" and 128 for a real failure, and the old code swallowed both alike, so a corrupt repository reported "index differs".

### Where the boundary falls

| Inside the sandbox | On the host |
|---|---|
| The repo's test suite | Clone, branch, commit, squash, push |
| Dependency installation | Indexing, retrieval, every LLM call |
| | Applying the patch **as text** |
| | Reviewer reading `git diff`, opening the PR |

The rule: **executing the repo's code goes inside; everything else stays outside.** Applying a patch is writing text, not executing it, so it does not need containing. No agent ever runs inside the sandbox — Verify is a stage, not an agent.

### The part that will actually cost the time

**Getting each repo's dependencies installed so its suite runs at all.** Not optional, fiddly per repo, and the reason SWE-bench ships a prepared image per repo. It also creates the one genuine tension with the security design: installing needs network, and network is the exfiltration path. Resolution: **network on during a separate build/install step, off during the test run.**

Related decision: **install dependencies once into an image, then start a fresh container per run from that image.** Reusing one live container across retry attempts is faster but lets state leak between attempts — a stale `.pyc`, a mutated fixture database — which quietly corrupts the benchmark. A fresh container from a prepared image pays the install cost once and still gives each attempt a clean filesystem.

**Implemented in `verify/`:** `spec.py` (per-repo `RepoSpec` from `verify/specs.toml`, plus the install heuristic for an uncurated repo), `dockerfile.py` (rendering the image, and the cache key that decides when it is rebuilt), `backends/docker.py` (`build_run_argv` and `DockerBackend`), `stage.py` (`Verifier`, the seam `run.py` calls). Four things in there are load-bearing and easy to undo by accident:

- **The image cache key covers the Dockerfile, the plugin's bytes and the dependency *manifests* — never the rest of the tree.** Keying on source would rebuild per attempt, and the baseline and the attempt would then have run in different environments. That is exactly the ambiguity the baseline exists to remove: `score` could no longer tell a suite the patch broke from one a differently-resolved dependency broke.
- **`build_run_argv` is pure and its test asserts each flag separately.** Every one of these fails *open*: a misspelled `--secutiry-opt` is rejected by the CLI and surfaces at once, while a dropped `--network=none` is simply a container with network and nothing about the run looks different. A golden-argv comparison would go stale and get regenerated rather than read.
- **The timeout path removes the container by name.** `run_process` kills the `docker run` client; the container is a child of the daemon and survives it, holding the memory cgroup and a bind mount of a directory the workspace is about to delete. `--rm` does not help — it fires on exit, which is what is not happening. This is why `container_name` is a required keyword on the Protocol and why it includes the task id.
- **The `docker` pytest marker is enforced by a `pytest_runtest_setup` hook in the root `conftest.py`,** skipping when no daemon answers and *failing* when `REPOLACE_TEST_DOCKER_REQUIRED=1`. The marker was declared in `pyproject.toml` before anything implemented it, so a daemon-backed test would have passed on a machine with no daemon — and the containment assertions are the ones that must never pass vacuously.

**What running it for the first time found, and neither was catchable by unit tests.** Both sides of each boundary were behaving exactly as written; only an actual container revealed the interaction.

- **The fingerprint was not stable, and it would have failed every task on every repository.** pytest names a plugin `getattr(plugin, "__name__", None) or str(id(plugin))`, and `PytestPluginManager` registers *itself* that way — so `fingerprint["plugins"]` carried a fresh memory address on every run. `fingerprint_changed` compares that list between baseline and attempt and `score` returns FAILED on a difference **before it looks at a single test result**. The benchmark would have been a uniform wall of confident, spurious failures. `_plugin_names` now counts unnameable registrations (`<anonymous:N>`) instead of naming them — counted rather than dropped, so a conftest registering an object of its own still shows as a difference. Pinned by `TestFingerprintStability` in `verify/tests/test_plugin.py`, which runs the real plugin twice in one directory and needs no daemon.
- **The sandbox left a `.pytest_cache` the host could not delete.** Written into the bind-mounted export as uid 65534 with mode 0755; deleting inside it needs write permission on a directory the host does not own, so `task_workspace`'s cleanup failed and every task leaked its temp tree. Fixed with `-o cache_dir=/tmp/.pytest_cache` — into the tmpfs, which dies with the container. `-o cache_dir` rather than `-p no:cacheprovider` so the `cache` fixture and `--lf` keep working, and `cache_dir` is not a fingerprinted ini option so it cannot read as configuration drift. **The general hazard remains** for any suite that writes into its own tree, and the remedy when it bites is the same one used to clear the stale dirs: delete them from inside a container, since the host cannot chmod files owned by a subuid.

**Rootless is a deployment precondition, not a preference.** Without cgroup v2 delegation, rootless Docker silently ignores `--memory`, `--cpus` and `--pids-limit` — the containment controls, failing open again. `docker info` reports the missing delegation as a warning; check it before trusting a run. Verified on the development host: `cpu memory pids` are delegated and the caps bind (`memory.max`, `pids.max` and `cpu.max` read back inside the container exactly as set). `cpuset` and `io.*` are **not** delegated, so `DockerLimits.cpuset_cpus` is silently ignored there — do not reach for it as a containment control without re-checking.

## Task success criteria (decided)

A task counts as successful when **the issue is resolved and the test suite passes without the agent having edited the tests** — the one exception being where editing a test is genuinely part of resolving the issue, because the test itself was wrong.

Operationally, scored as fail-to-pass plus pass-to-pass:

1. **Baseline.** Before applying any patch, run the suite in the sandbox and record which tests pass and which fail. Without this, "the tests pass" is unfalsifiable — a repo with pre-existing failures would score as a failure no matter what the agent did.
2. **Fail-to-pass.** The tests targeting the issue must go from failing to passing.
3. **Pass-to-pass.** Everything that passed at baseline must still pass. This is what catches a fix that trades one bug for another.
4. **No test edits**, by default. A diff touching test files fails the task.

**Amendment (a false PASSED, found by audit and reproduced).** "Fail-to-pass" was implemented as `baseline.failed ∪ baseline.skipped` intersected with `attempt.passed`, on the reasoning that pytest reports an xfail as a skip. It does — but so does every *ordinary* skip, and a real suite is full of them: `importorskip` for an optional dependency, a platform guard, a marker gate. A baseline skip that started passing for any reason at all — a dependency appearing in the image, an install-step change — then scored the task **PASSED with nothing red at the base commit**. That is the failure mode this whole section exists to prevent: not a point lost, but a pass nobody could defend.

The report parser now separates `xfailed` from `skipped`, using the `xfail` flag the plugin already recorded and the host discarded. The flag is **per-phase** (pytest sets `wasxfail` on the `call` report, so the surrounding phases carry False) and is **also** set on a non-strict xpass, which is a `passed` record — so the rule reads it only off the record that carried the skip. Three consequences, load-bearing *together*:

- **fail-to-pass** joins on `failed ∪ xfailed`. An ordinary skip going green is no longer evidence of anything.
- **neutralized** counts `xfailed` as silenced. Marking a baseline failure `@pytest.mark.xfail` is the cheapest possible way to make it stop objecting, and separating the buckets without this would have opened a wider hole than it closed.
- **admissibility** gates on the same `failed ∪ xfailed` expression, through one shared function so the two cannot drift. The old gate read `not failed and not skipped`, so a single ordinary skip made an unscoreable instance look scoreable; it then fell through to "no baseline-failing test now passes" and scored FAILED — an instrument limitation charged to the agent, on most real repositories.

`task_test_runs.xfailed` (migration 0010) exists for the reason 0009 gives for the sets it added: a dropped set cannot be recovered, and "was this an xfail or an ordinary skip" is exactly the question this revision had to ask.

**Amendment (the exemption was too wide).** Point 4, "no test edits", is enforced by `disqualifying_paths`, which combines what pytest actually collected with a path heuristic and then *exempts* a heuristic match that existed at the base commit — so a shipped module like `django/test/client.py` is not mistaken for a test. That exemption was exempting far too much. `tests/helpers.py`, `tests/__snapshots__/*` and `tests/cassettes/*` all existed at baseline and pytest collects tests from none of them, which is exactly the signature the exemption keyed on — so all three were freely editable, and editing a golden file or a recorded cassette is the cheapest fake fix there is. `_FIXTURE_DIR_PARTS` was protecting nothing whenever `baseline_files` was supplied.

The exemption now applies only when no *test-named ancestor directory of the file* is one pytest collected tests from. `django/test/client.py` is readmitted (nothing was collected at or under `django/test`); the three above are refused.

Two boundaries in that rule are deliberate, and loosening either breaks honest work rather than catching cheating: the directory must be **test-named**, or `myapp/models.py` beside Django's `myapp/tests.py` would be disqualified; and the repository root is excluded from the collected-directory set, because it is an ancestor of everything. Narrowing the *exemption* rather than adding a new disqualifying branch keeps both safe by construction — `is_test_path` is False for those two paths, so they never reach the exemption at all — but the tests pin them anyway, because the alternative shape is what someone simplifying this later would reach for.

The acknowledged gap: a repository whose tests sit at the top level gets no tree rule, only the heuristic and the collected-file set.

**The exception is the hard part.** "Unless the test itself was wrong" is not machine-checkable — an agent that cannot pass a test can always claim the test is at fault, and that is precisely the loophole it will find. An unfalsifiable escape hatch would quietly destroy the credibility of the benchmark number, which is the project's whole differentiation claim.

So the exception is a **separately tracked outcome, never a silent pass**:

| outcome | meaning |
|---|---|
| `passed` | fail-to-pass + pass-to-pass, source changes only |
| `passed_with_test_edit` | as above, but the diff touched tests; requires the agent to state why, and human sign-off before it counts |
| `failed` | anything else |

The headline benchmark figure is **`passed` only**. `passed_with_test_edit` is reported alongside it, never folded in. If that second bucket grows, it is a signal the agent is learning to argue with tests rather than fix code — worth watching as its own metric.

**Decided since (these were "still to pin down"):** the agent may **not** add test files. The leaning recorded here was yes, and it was reversed when the toolbox was built. The mechanical reason is that a test file the agent adds is one the scorer rejects regardless: `disqualifying_paths` applies the path heuristic to any file that did not exist at the base commit, so a task whose diff adds `tests/test_new.py` fails with "diff touches test or config files", and letting the tool create one would only waste the run. (The project plan lists "agent may not add test files" among its settled decisions; the further reasoning is not recorded in the sources this section was written from.) `create_file` therefore refuses test and configuration paths exactly as `edit_file` does (the shared `is_protected` write guard), the system prompt says so in as many words, and the tool's refusal tells the model to reproduce behaviour with `run_python` scratch scripts instead. Still open: whether diff scope should be capped by file count or line count. **Nothing caps it today** (no file- or line-count check exists in `agents/`, `pipeline/` or `verify/`); a patch is bounded only by the step, attempt and budget caps and by what the write guard refuses.

**Where this lives in the schema (migrations 0007 and 0011).** Until then none of the above was expressible — the project's headline claim had no table behind it.

- `tasks.outcome` is a separate enum from `tasks.status`, because they answer different questions: status is how far the pipeline got, outcome is whether the issue was fixed. Both are needed; neither substitutes for the other.
- `task_test_runs` holds one row per suite execution — attempt 0 is the baseline, 1..N are the bounded retries — storing the raw `passed`/`failed` sets rather than derived fail-to-pass and pass-to-pass lists. The scoring rule still has open questions above, so keeping what it is computed *from* means the benchmark can be rescored without re-running anything. A run that produced no usable result at all (import error, missing dependency, timeout) sets `error`, which is what makes a task *unscoreable* rather than failed.
- Migration 0011 adds `collected_files`, `conftests`, `fingerprint` and `stdout_tail`, and the first three are read by the rule rather than merely nice to have: `disqualifying_paths` joins on what pytest actually collected, and `fingerprint_changed` refuses to compare two runs whose rootdir, watched ini options or registered plugins differ. Without them a stored run cannot be rescored, only re-run — which defeats the reason 0007 stores raw sets at all.
- The test-edit exception is enforced by check constraints, not convention: `passed_with_test_edit` without a justification cannot be inserted, and sign-off cannot be recorded on any other outcome. The one part of the criteria that is not machine-checkable is at least made impossible to record silently.

**Unrelated trap found while doing this, now fixed:** migration 0004 creates the GIN index on `content_tsv` and the HNSW index on `embedding` — both arms of hybrid retrieval — but neither was declared in `CodeChunk.__table_args__`. The model and the database therefore disagreed, and `alembic revision --autogenerate` emitted a `drop_index` for each. The next autogenerated migration would have deleted the indexes retrieval depends on, with nothing failing to show for it. Both are now declared on the model, and `alembic check` is clean. **Run `alembic check` after touching models** — it is what caught this.

## Verify extensions for an agent (decided)

Verify was first built for a pipeline that ran the suite twice. An agent that reads test output and runs code needs more, and each addition is a new way for it to learn something it must not, or for one run's result to be mistaken for another's. The rules below exist for those two failures.

**Three kinds of run, with deliberately different rules** (`verify/verify/stage.py`):

| | scored (`Verifier.run`) | probe (`run_subset`, the `run_tests` tool) | script (`run_script`, the `run_python` tool) |
|---|---|---|---|
| key | `int` attempt: 0 baseline, 1..N | `probe-<n>` | `script-<n>` |
| hidden-test overlay | yes, every scored run | **never** | **never** |
| recorded in `task_test_runs` | yes | no | no |
| counts toward the "baseline already ran" guard | yes | no | no |
| source mount | per spec (`repo_readonly`) | per spec | `:ro`, unconditionally, not via a spec field |
| directories | kept with the workspace | `discard`ed in a `finally` | `discard`ed in a `finally` |

A `str` label must start with a letter and be at most 64 characters, so it can never read as an attempt number (`"1"` would otherwise give the same directory and container name as the int 1). Counters only advance, so a label is never reused, not even after its run was discarded: the export is written in place and the plugin *appends* to `report.jsonl`, so a reused label would mix two runs. A probe needs the environment the baseline built and raises `VerifierNotReady` rather than building one from a tree the agent has already edited (that would break "built once, from the base commit"). A `SandboxError` from a probe or script is **returned** (`SuiteResult.error`, `ScriptResult.error`), never raised; `VerifierNotReady` is the only exception, so the tool layer has exactly one thing to catch. A scratch script is written beside the report, outside both the checkout and the export, and is mounted read-only at a fixed path with a file name no repository has (`/scratch/_repolace_script.py`), because `sys.path[0]` is the script's own directory and a script called `main.py` would shadow a repository module. The checkpoint commit before a probe lives in the *tool*, not the verifier, so `verify` stays git-free.

**The hidden-test overlay** (`verify/verify/overlay.py`). A benchmark instance carries the test files its fixing PR added or changed. They are laid over the *export* at run time, after the environment is built, so they are never baked into an image layer the cache shares and are not in the cache key. Values are **complete file bytes**, not a diff: SWE-bench ships `test_patch` as a diff, instance preparation applies it once on the host and stores the resulting files, so nothing at run time parses or trusts a patch. Every key goes through `resolve_within` and is refused if absolute, containing `..`, containing a `.git` component at any depth, a backslash or NUL, non-canonical, under a symlinked or file parent, an existing directory, or nested under another key; nothing is written if any key is bad, and the keys are validated when the `Verifier` is constructed so a bad one fails before a forty-minute build rather than after it.

**Two verdicts, one set of preconditions.** `score()` is the benchmark's: it returns an outcome, or *inadmissible* when the instrument failed. `agent_verdict()` is the non-benchmark PR gate: `ok` means only "no regression, silenced failure or new collection error was found", never "the issue is fixed". `score()` cannot be the gate because it is inadmissible whenever nothing was red at the base commit, which is the normal case for a live issue (the suite passes; the bug is simply not covered), so under it a real task would never open a PR. Both call `_preconditions` (disqualifying paths, unusable baseline, infrastructure error, unscoreable attempt, fingerprint drift), and `TestAgreesWithScore` pins that they report the same reason, so the PR gate and the benchmark cannot disagree about what a run means. `expected_not_red(baseline, expected)` returns the curated fail-to-pass ids that were **not** red at the base commit. Without it, an expected test that already passes in our environment lets every other condition of `score` be met by a patch that changes nothing, and a comment-only edit would score PASSED. The pipeline checks it **before the agent runs** and completes the task as inadmissible if it is non-empty; the gold analysis checks it per instance.

**`is_protected_path(path, *, collected_files, conftests)` is what the edit tools refuse to write**, and the pipeline passes a baseline-aware version (`protected_check` in `pipeline/repolace_pipeline/agent_context.py`) as `ToolContext.is_protected`. The context's default is the baseline-blind function, which would let the agent edit a file pytest collects through a custom `python_files`, after which the scorer discards the whole patch. Two directions, stated so nobody "fixes" either: it is **never weaker** than `disqualifying_paths` (a test asserts it over a grid of paths), and it is **stricter on purpose**: at edit time it has no `baseline_files` evidence, so it refuses a shipped module like `django/test/client.py` that the scorer would spare, which means an issue whose real fix lives in such a module cannot be fixed by the agent. It also protects `.github/`, which the scorer does not. The baseline it is built from has the benchmark overlay's paths **removed**: a refusal that said "that file is read-only" for a path the agent has never seen would be an existence oracle for a hidden test file. The cost is accepted: an agent that writes over a hidden collected file wastes an attempt, because the scorer, which reads the unfiltered baseline, disqualifies it.

**Pytest argv, and why each addition is there** (`build_run_argv`; every pytest run, baseline, attempt and probe, gets the same ones):

- `--rootdir=/repo`, always. With no ini file pytest derives rootdir from its arguments, so a run given `tests/test_a.py` can root at `/repo/tests` and every node id lose its prefix; a probe's ids would then match nothing the baseline recorded. One rootdir is one node-id space, and the plugin fingerprints `rootdir`, so the baseline/attempt comparison cannot drift on it. (This changes the fingerprint's `rootdir` for runs recorded before it; none existed outside tests.)
- `-o cache_dir=/tmp/.pytest_cache` (already recorded above) and `-o addopts=` unless the spec keeps its own.
- `--continue-on-collection-errors`, unconditional and not a spec field. Without it pytest stops the whole session at the first collection error (exit 2, nothing run, `passed` empty): a module the patch broke, or a hidden module that cannot be imported, would hide every other result, two attempts differing only in whether a hidden file imports would give the agent different feedback, and `new_collect_failures` and the baseline's own broken modules would be dead code. With it the run exits 1, `collect_failures` is populated and the rest runs. **This is more lenient than SWE-bench, where any collection error kills the run**, so a score from this harness is not interchangeable with one from theirs, and the report's predictions export (below) is a cross-check, not an equivalence.
- The per-run nonce reaches the container as `-e REPOLACE_RUN_NONCE` (the **name only**); the value is in the docker CLI's own environment, which the CLI forwards. Argv is world-readable (`ps`) and is logged on a timeout, the same reason the git credential never travels in argv.

**Report integrity: the confused deputy again.** The sandbox owns the results directory the host later reads `report.jsonl` from, so whatever is at that path is whatever the code under test left. Review found that `parse_report` followed a symlink there: a probe (which does not carry the overlay) could point it at *another run's* report, such as the baseline written **with** the hidden tests laid over, and the host parsed it as the probe's own and handed the hidden node ids and outcomes back through the `run_tests` tool. Reproduced against the parser, with no Docker; that the sibling's host path is discoverable from inside the container (via `/proc/self/mountinfo`, which shows the bind source) rests on standard Linux behaviour and was **not run inside Docker**. A second route, an error message that carried a host path (a `chmod 000` report), was found in the same review and closed with it. The class is the one this file already names: nothing escaped, the sandbox wrote a file and the host voluntarily read it. **Now:** the host opens the report with `O_NOFOLLOW | O_NONBLOCK`, refuses anything that is not a regular file by `fstat` on the descriptor (so the thing checked is the thing read), caps its size (`MAX_REPORT_BYTES`, 64 MiB), and requires the per-run nonce on the plugin's `start` and `session` records, so a report from another run is refused even if the symlink check ever regresses (a hard link cannot cross bind mounts). The nonce is integrity against *substitution*, not authentication of the code under test: that code shares the container and its environment with the plugin, so a forged report written by the same run is accepted, by design. See the residual risks under "The no-oracle protocol".

## The agent (decided)

**Shape: a hybrid graph.** The outer graph is fixed and small, the agent node is a bounded tool loop (`agents/repolace_agents/graph.py`). As built it is `localize -> agent -> verify`, then a conditional edge (`route`) back to `agent` or to the end. The plan's sketch was `localize -> agent -> verify -> decide -> finalize`; `decide` is that conditional edge, and **there is no `finalize` node**: scoring, the PR gate, the squash, the push and the final database write need git, Postgres and GitHub, so they live in the pipeline (`run_task`), after the agent returns an `AgentResult`. `localize` makes no model call; `agent` is the only node that calls the model; `verify` is the only node that reads the oracle, and only to hand it to the feedback filter. State is a frozen dataclass in which **every field has a default** (LangGraph builds it as `schema(**input)`, a fresh instance per node), and dependencies travel in the run context, not the state. The recursion limit is a guard, `4 * max_attempts + 8` (the default is 10007, effectively unlimited), so a routing bug becomes a `GraphRecursionError` within a dozen steps instead of a model call per step until the budget ends it. Phase 1 deliberately keeps **one agent, not split by role**; Phase 2 splits it after seeing where this one overloads.

**The pipeline calls `run_agent`, never `run_graph`.** `run_agent` draws a fresh `secrets.token_hex(8)` delimiter nonce per call and takes no parameter for it, because a nonce a caller can choose is one an attacker can predict. `run_graph` takes the nonce only so a test can fix it.

**Bounds.**

| bound | value | where |
|---|---|---|
| attempts | 3 (`AgentLimits.max_attempts`) | a retry happens only on a *fresh*, not-clean scored attempt, with attempts left and no infrastructure fault |
| steps (model calls) per attempt | 40 | `STEP_CAP` when reached |
| tool calls executed per model reply | 8 (`MAX_TOOL_CALLS_PER_REPLY`); the rest are answered "not executed", never run | the injection audit scripted a single reply of 3,000 calls and all were executed, each `run_python` up to 120 s |
| task cost | $2.00 (`DEFAULT_MAX_USD`) | the gateway, not the agent |
| model calls per task | 150 (`DEFAULT_MAX_CALLS`) | the gateway; 3 attempts x 40 steps is at most 120 |
| wall clock per task | 3600 s (`DEFAULT_MAX_WALL_SECONDS`) | the gateway; **started when the agent stage starts** (`_agent_budget`), not at the task's start, so a clone, an index that waited twenty minutes for another task's lock and a baseline run cannot eat the cap and charge an instrument limit to the agent |

The budget is also checked between tool calls, not only inside the next model call, because a reply's calls can each run for minutes. A budget stop does **not** append the response that crossed the line (its tool calls cannot run, and an assistant message whose `tool_calls` have no answers is rejected by the provider on the next call). `UnpricedModelError`, `MissingProviderKey`, `NoTaskScope` and anything else propagate: they mean repolace is misconfigured, and a task that fails loudly is worth more than one that quietly reports a stop reason. Only the `agent` stage is called in Phase 1; the `cheap` stage is required by the gateway config and unused.

**The nine tools** (`agents/repolace_agents/tools/`), plain async functions with JSON schemas that `ToolBox` **enforces** (`enum`, `minimum`, `maximum`, `minLength`, `maxLength`, `minItems`, `maxItems`, `items.type`; it refuses at construction a schema using a keyword it does not enforce, so a schema never advertises a bound nothing checks). Every result is capped at 8,000 characters. A model-visible failure (`ToolError`) becomes an error result; anything else is repolace's bug and propagates, so a broken tool cannot pass for a model that is bad at using it.

| tool | what it does | bounds |
|---|---|---|
| `search_code` | the index, through an injected callable that opens its **own short-lived session** per call | query 1-500 chars, limit 1-20 (default 8) |
| `read_file` | numbered lines | at most 400 lines a call; files over 1,000,000 bytes refused |
| `grep` | `git grep` over *tracked* files | below |
| `list_dir` | entries to a depth | depth 1-3, at most 300 entries |
| `edit_file` | exact, unique match | `old_string` and `new_string` at most 20,000 chars |
| `create_file` | a new, non-protected file | at most 100,000 chars |
| `run_python` | a scratch script in the sandbox, no network | code at most 20,000 chars, timeout 1-120 s (default 60) |
| `run_tests` | a probe: some visible tests, not scored | at most 20 targets, probe timeout 300 s |
| `submit` | ends the loop | summary 1-4,000 chars, no control characters |

**What bounds them.** Every path goes through one function (`tools/paths.py::confine`, built on `resolve_within`): empty, over-long (500 chars), control-character or backslash paths, `..`, absolute paths and **any symlink anywhere in the path, even one that lands back inside the tree** are refused, because following it would let the repository choose where a later read or write goes. Anything with a component starting `.git` (`.git`, `.gitignore`, `.gitattributes`, `.gitmodules`, `.github`) is refused for reads too, case-folded, with HFS-ignorable code points stripped and the NTFS short name `git~1` refused. For **writes**, additionally, any component starting with `.` is refused (default-deny: `.circleci/`, `.travis.yml`, `.vscode/`, `.devcontainer/`, `.husky/`, `.envrc`, ...), plus root-level CI definitions that are not dotfiles (`Jenkinsfile`, `azure-pipelines.yml`, `appveyor.yml`, `cloudbuild.yaml`, `bitbucket-pipelines.yml`), plus `ToolContext.is_protected`. The dotfile rule replaced a `.git*`-only guard after the security review showed the `.git*` prefix covered `.github` but left a dozen other CI and editor-hook locations writable (see the known limit below for what a deny list still cannot cover). `grep`'s argument vector is built to one rule: **a model-supplied string is never placed before `--` and is never an option**: the pattern is the operand of `-e`, the path follows `--`, and `--literal-pathspecs` stops git reading the path as pathspec magic or a tree-ish. `-E` is glibc's regex engine, which is not safe against a hostile pattern (a 28-character nested counted repetition was measured at about 5 GB resident), so the child runs **resource-limited**: `prlimit --as=512MiB --cpu=15:20 -- git ...`, `--threads=1`, a 20 s wall clock, output read back to at most 1 MiB, the whole process group killed on timeout, and patterns with a backreference or a counted repetition bound of 100 or more are refused up front. `prlimit` is a host dependency (see "Deployment requirements"). `run_tests` targets must match a safe path pattern whose first character is never `-` (an option) or `@` (pytest expands `@file` into arguments), must name a file that exists and passes the read guard, and are normalised before use (`./-x` would otherwise become the option `-x`). **No new test files:** see "Decided since" under the success criteria.

**Retries and feedback.** After `submit` (or a step cap) the pipeline scores the attempt; if the feedback filter finds visible regressions or collection errors and attempts remain, the model gets one message and another attempt, with earlier tool outputs replaced by `[output from attempt N elided]` (the assistant messages and their `tool_calls` stay, so every call still has an answer and the transcript stays valid). A transcript over 400,000 characters has its older tool results elided mid-attempt too, sparing the newest six; past that the next request would fail with a context-window error, which is `LLM_ERROR`, which skips verify, so the work would never be scored. Earlier edits **persist** between attempts (nothing resets the tree; only the end of the task rewinds, to the last scored commit). An attempt whose tree is identical to the last scored one is not scored again.

**Stop reasons** (`agent_stop_reason`, eight values behind a CHECK constraint): `submitted`, `step_cap`, `budget_usd`, `budget_calls`, `budget_wall`, `llm_error`, `no_change`, `max_attempts`. `max_attempts` was added after review: without it "submitted clean" and "gave up after three red attempts" were one bucket in the report. It is set when every attempt was used and the last scored one still had visible regressions or collection errors; a clean last attempt keeps the agent's own reason. After a budget or LLM stop verify is **skipped**: the loop was cut short, so the tree may be half-edited.

**Models.** The `agent` stage routes to `claude-sonnet-5-5` (the headline model, `gateway/models.toml`); **its `[price]` table is commented out and must be filled in by the maintainer** before any call, because the gateway refuses an unpriced model (`UnpricedModelError`) rather than record the call as free, and rates were deliberately not guessed: a wrong price is a wrong benchmark. Comparison columns are one run each of an OpenAI and a Gemini model, declared as `comparison-a`/`comparison-b` placeholders in the same file and selected per sweep with `GATEWAY_STAGE_MODELS='{"agent": "<key>"}'` (`repolace-eval run --model <key>` sets it). The provider must be one of `anthropic`, `openai`, `gemini`, and `litellm_model` must start with `<provider>/`, checked at load, so one vendor's key is never sent to another vendor's API.

## The no-oracle protocol (decided)

In benchmark mode the hidden fail-to-pass tests are the answer key. If the agent could see which of them are red it would iterate against the key, and the benchmark would measure how well it reads the key. So the rule is: **hidden FAIL_TO_PASS tests never reach the agent**, and everything below is how that is held.

- The overlay goes onto the *export*, never the checkout, so no tool can read the hidden files; probes carry no overlay, so `run_tests` cannot run them.
- **The feedback filter (`agents/repolace_agents/feedback.py`) is the only place a *scored* `SuiteResult` becomes text a model can read.** (A probe's result is rendered by the `run_tests` tool, which is safe because a probe never includes the overlay, and the pipeline filters it anyway as defence in depth: `visible_probe`.) The filter drops node ids and collection failures whose path *is* or lies *under* an overlay path; rebuilds the result from an empty `SuiteResult` copying only the fields the verdict reads, so a field added later fails closed; computes counts, regressions, neutralised failures and the verdict **from the filtered pair**, so a count cannot encode a hidden test; and drops `stdout_tail`, `exit_code` and `duration_seconds`.
- **Fail-closed overlay mode, keyed on `issue.instance_id is not None`** (or a non-empty `hidden_paths`), not on `hidden_paths` alone: keying on the overlay's contents would let an empty overlay silently turn the protection off. The filter's `overlay_mode` parameter itself defaults to True.
- **An id is shown only if the filtered baseline run produced it.** The scored run executes the agent's own source in the same interpreter as the report plugin, so a node id on a visible path is text the agent's code chose; ids outside the baseline's universe are counted (capped), never named.
- **One neutral sentence for any errored scored run** in overlay mode, because the categories (timeout, out of memory, did not finish) are themselves hidden-dependent: a hidden test that hangs, one killed for memory and a hidden module that does not import each used to give a different message, and the old wording blamed "the visible test run" for all of them. **Baseline totals are dropped** in overlay mode: an overlay usually *replaces* an existing test file, so the filtered totals are short by exactly that file's tests, and subtracting them from an overlay-free `run_tests` probe names the hidden file.
- **One phrasing for "there are tests you cannot see": "Some tests are not shown to you."** Identical in product and benchmark mode, used verbatim by the system prompt, the retry message, the baseline summary and the tool descriptions (a test holds the tool copy equal to `render`'s). It is honest without saying how many hidden tests exist, which files hold them or what they are called, and without the words "visible" and "hidden", which turn a fact into a thing to probe for. `hints_text` (SWE-bench's discussion comments, which often contain the fix) is not a field the agent's `IssueContext` has. The issue number, the URL and the `instance_id` *are* fields of it (the last is what switches the feedback filter into overlay mode), but none of them is rendered into a prompt: `build_localize_message` reads only the title and body.
- **Tripwires, so a future edit cannot quietly route around the filter** (`agents/tests/test_graph_oracle.py`, `agents/tests/test_feedback.py`): a sentinel planted in every field of the baseline and every attempt result, run through the whole multi-attempt loop, with a control that proves the search *can* find it where it is allowed; an AST scan that the prompt-building modules, the graph and the tools never touch `baseline` or an attempt's `result` outside the filter; a metamorphic test (change only the hidden tests and the transcript must not change); and a graph-differential test (hidden red or green must not change the attempt count, the stop reason or the spend).

**Residual risks, stated plainly** (from the Model QA and injection audits of the graph; none is closed):

1. **A deliberately adversarial agent can still signal.** The scored run executes the agent's code, so it can forge the report or encode bits in *which visible tests it makes fail*; a regression pattern is information the agent is entitled to and is not hidden-test text. The id universe stops it carrying free text, not signalling through visible ids.
2. **One bit per attempt: "did the scored run complete".** An errored scored run is one sentence, but still a different message from a completed run, and hidden tests can cause it (a hang, a memory kill, a module that does not import). The retry policy is a deterministic function of that bit (not clean, so retry while attempts remain and end `max_attempts` otherwise, unless the sandbox itself failed, which is never retried).
3. **A replaced test file's regressions are invisible to the feedback**, though the *scored* verdict still enforces pass-to-pass on the unfiltered results. Feedback just does not warn the agent.
4. **A hidden `conftest.py` or helper can change visible outcomes** under the overlay, or the run's fingerprint (a plugin registered only when some behaviour is present), so a correct fix can be reported as "the test configuration changed" and retried. In overlay mode the message is one sentence with no plugin or ini names, which leaves one bit.
5. **Hidden tests are readable by the code under test during a scored run.** They sit in the container's `/repo`. Only the feedback filter hides them from the *model*; the sandbox does not.
6. **A timing channel, many bits per attempt, which bypasses the feedback filter entirely.** Because of (5), the agent's code in a scored run can read the hidden tests and sleep for a duration that encodes their contents; the agent brackets the run with two `run_python` calls that print the time (one before `submit`, one in the next attempt), and since containers read the host's realtime clock the difference recovers the delay, give or take model latency. At one-second granularity against a 1,800 s suite timeout that is on the order of 10 bits per attempt, far more than the "one bit" residuals above, and no field of the result carries it, so the filter cannot see it. It needs a deliberately adversarial agent, like (1). **Not mitigated, and the cheap ideas are weaker than they look:** a Linux time namespace offsets only `CLOCK_MONOTONIC` and `CLOCK_BOOTTIME`, not the realtime clock, and a faked clock inside the container (an `LD_PRELOAD` shim such as libfaketime) is bypassed by any direct syscall; padding every scored run to a fixed duration would work and costs the suite timeout on every attempt. The deferred design below (feedback from a run without the hidden tests, the scored run once at the end) closes it by construction: the hidden tests are never present while the agent can still act.

**Considered and deferred.** Feedback from a separate, overlay-free run, with the scored run happening once at the end, removes every channel above by construction, the timing channel (6) included. Phase 1 did not take it because it roughly doubles suite executions (the dominant cost and wall time of a task) and changes the `AttemptRecord`/`task_test_runs` contract, which the pipeline, the report and every stored row are built on. The filter closes every *accidental* channel; what remains needs an adversarial agent or a rare repository. Revisit it if the benchmark is ever used to compare agents that might be adversarial rather than merely capable.

## Prompt-injection posture (decided)

Issue text, retrieved snippets, test ids and test output reach the model, and all of it can be written by someone who is not the repository owner. **The agent's authority comes from its tools, not its prompt**: the prompt asks the model to refuse injected instructions, a test pins that a hostile issue changes neither the tool list nor the system prompt (apart from the nonce), and the real bound on a hostile issue is what the tools can do, which is why the confinement above is code rather than a request.

- **Nonce-delimited framing.** Untrusted text sits in blocks tagged with a per-task nonce (`<issue-<nonce>>...`). Before it does, it is cleaned in a fixed order (`agents/repolace_agents/render.py`): length pre-cut generously so the work is bounded by what will be sent, invisible and control characters removed or escaped, **closing tags neutralised in one pass**, then cut. The closer of every tag family (`issue`, `repository`, `retrieved`, `baseline`, `feedback`, `output`, with any suffix) has its leading `<` replaced by `‹`, so the defence does not rest on the nonce staying secret. Neutralising rather than deleting is the fix for a finding: deleting needed a fixpoint (deleting `</issue-x>` from `</iss</issue-x>ue-x>` assembles a new one) and a fixpoint is quadratic on nested payloads, where 64 KB of them froze the event loop for about 5 s; replacing the `<` creates no new `<`, so one linear pass suffices.
- **At most 8 tool calls executed per model reply**, a transcript budget with elision (400,000 characters, newest six results spared), and **malformed tool-call arguments replayed as `{}`**: the gateway keeps `raw_arguments` verbatim, but replaying unparseable text (truncated JSON, single quotes, two concatenated objects) made LiteLLM's message converter raise a non-transient error while building the next request, which became `LLM_ERROR`, which skips verify. The model is still told what it got wrong, in that call's tool result. (The audit rated this latent: LiteLLM's Anthropic response path re-serialises arguments, so the kill needs another provider's arguments replayed through an Anthropic-style converter.)
- **`submit.summary` is sanitised once** (NUL, control, format and surrogate characters removed, capped at 2,000 characters) and then, wherever it is shown, quoted as the agent's claim in a fenced block and put through the PR writer's neutraliser (raw HTML and images stripped, `@mentions` and bare `#123` / `owner/repo#n` broken with a zero-width space, entities and reference definitions handled). Either alone would stop most inputs; both are there because the failure is a mention that pings a real person, an issue reference that notifies an upstream project, or an image URL that carries data out. A benchmark PR shows the summary too, through the same sanitiser and fence (`_section_summary` has no benchmark branch, and `test_even_a_hostile_summary_cannot_put_a_reference_into_a_benchmark_body` pins that it is defused there, not that it is absent). It is kept out of every *commit message*, product and benchmark alike, because that is the text a later run clones.
- **Invisible characters in tool output are escaped, not deleted** (`escape_invisible`), so the text still matches what `edit_file` is given. ZWJ and ZWNJ are kept because real text needs them.
- **Product PRs say `Refs #N`, never `Fixes #N`**; a benchmark PR has no `Refs`, no URL and no `#`-reference anywhere, in the title, the commit message or the body: `#N` in a bench repository resolves to an unrelated object and an upstream URL posts a backlink on the real upstream issue. A benchmark commit message carries no outcome-bearing text either, because it is pushed to a repository the next run clones in full.

**Known limit, recorded and not fixed: any non-protected file is writable, including files that CI or a build executes** (`Makefile`, `setup.py`, `noxfile.py`, `scripts/ci.sh`). A deny list cannot close this without banning build files in general, which would make many real issues unfixable. The mitigations are positional, not technical: benchmark repositories are private with Actions disabled before the first push; and **in product mode, do not push an agent branch to a repository where push-triggered CI has secrets without making that decision deliberately**. repolace pushes the agent branch to the same repository the PR targets, so such CI would run agent-authored code with the project's secrets before any human has looked. This is the same trust question the "PR conversation handling" vision flags, and it needs an answer before product mode is pointed at a repository that is not the operator's own.

## The benchmark (decided)

Phase 1's claim is a number, so the harness (`eval/harness/`, the `repolace-eval` command) is built to make that number hard to inflate. **It exists and is tested; no sweep has run, so there is no number.** The stages in order: `select`, `fork`, gold validation (`enqueue --agent gold`, `run --agent gold`, `gold`), the sweep (`enqueue`, `run`), `report`, and separately `retrieval`.

**Instances: a filtered subset of SWE-bench Verified, not the official set** (`select_instances.py`). The allowlist of repositories (`pytest-dev/pytest`, `pylint-dev/pylint`, `psf/requests`, `pydata/xarray`, `sphinx-doc/sphinx`, `mwaskom/seaborn`, `pallets/flask`) is the maintainer's recollection of which Verified repositories are pure-Python pytest projects and only bounds what is worth cloning; **the filters decide**. `django` (its own runner) and `sympy` (`bin/test`) are out, and so are `astropy`, `matplotlib` and `scikit-learn`: the image installs into `/repo` and every run then bind-mounts the export over `/repo`, so anything an install generates *inside the tree* (a `setuptools_scm` `_version.py`, in-tree compiled extensions) is masked at run time and such a suite is unscoreable by construction. An instance must survive, in order, and the first failure is its recorded reason: a complete, untruncated row; a non-empty `FAIL_TO_PASS` and a well-formed id and `base_commit`; a test patch touching only `is_protected_path` files, adding or modifying only (no delete, rename or binary) and no dependency-manifest name; a **simple-fix filter**, meaning a gold patch that touches no protected path, no `.git*` component and nothing under `.github/` and deletes or renames nothing (the agent's edit tool refuses those paths, so such an instance is unfixable and would inflate the denominator, at the price of a set that skews toward pure source edits); an entry in the SWE-bench environment snapshot that can be built (Python 3.8 or later, or no system packages, because old Debian images have archived apt repositories); no tracked symlink or gitlink at the base commit (the byte-identical export refuses both); both patches pass `git apply --check`; every post-apply file is valid UTF-8. **Patches are applied to a git index, never a checkout**: no working tree exists, so no filter, `eol` conversion, hook or symlink can act, and the stored bytes come straight from blobs. Selection is deterministic: candidates are ordered by `sha256(seed:instance_id)` and taken round-robin across repositories under a per-repository cap (`--max-per-repo`, default 6) until `--count` (default 25) pass; the **seed (default 0) is a degree of freedom, so it must be fixed and recorded before the first agent run**. There is no automated preference for fast suites: gold validation records each suite's wall time and *proposes* `targeted_p2p`, and the maintainer prunes by hand. The SWE-bench environment snapshot, `eval/harness/swebench_specs.json`, is **not committed**: it is generated once by the snippet in `harness/specgen.py`, which says it was written without network access and has not been run.

**Instance files** are `eval/instances/<id>.json` (`InstanceSpec`, `shared/repolace_shared/instances.py`): the overlay (`test_files`) as **complete file bytes**, `fail_to_pass`, `pass_to_pass`, `gold_files` (the complete post-fix files, `repr=False` so a stray log line cannot print them), a raw `spec` mapping that `verify.spec.spec_from_mapping` consumes, and the `problem_statement`. The *reference fix as a diff* is a separate `<id>.gold.patch` sidecar that only the retrieval eval reads. **Be exact about what the pipeline loads:** it never loads the sidecar, but in benchmark mode it does load the instance JSON, `gold_files` included, because the gold runner needs them. Nothing hands them on: `IssueContext` and `AgentDeps` have no such field, and `shared/instances.py` states that `gold_files` "must never reach an agent, a prompt, or a tool result". An id that came from a database row is only ever resolved with `load_instance_by_id`, never by building `dir / f"{id}.json"` by hand.

**Benchmark repositories** are private `repolace/bench-<instance_id>` repositories in the existing organisation, which also hosts `repolace/repolace`; that is why the guardrails *are* the design (`harness/bench_repos.py`, run by `repolace-eval fork`). `check_bench_name` is the one decision about what may be touched, enforced a second time on every outgoing request path by an allow-list and a third time where the push leaves the process (a credential-free `repolace/bench-*` URL and exactly one refspec, `<base commit>:refs/heads/main`). **A repository the tool did not create is never adopted or deleted**: each one it creates carries a marker description, a 422 "already exists" is followed only for a private repository with the marker, and `--delete` re-reads the repository immediately before each DELETE (an earlier version recorded a pre-existing `bench-*` repository as ready and would then have deleted it). Each is created private with issues and wiki off, and **Actions are disabled before the first push**, because a workflow in the upstream tree, run by the push of the base commit, would otherwise run with that repository's own token; if any later step fails the repository is recorded `status = "incomplete"`, which only `--delete` may use. No parser accepts an abbreviated option (`fork --de --y` must not mean `--delete --yes`). **The token (`REPOLACE_BENCH_GITHUB_TOKEN`) goes inline on the one command and is never put in `.env`**: `infra/docker-compose.yml` gives the `api` service `env_file: ../.env`, so a token there lands in the environment of an internet-facing container. The module recommends a dedicated bot account that is a plain organisation member in no team that reaches the product repository, a classic `repo` token with a 7-day expiry (and `delete_repo` only for the cleanup run), and installing the App on "selected repositories"; it also says that pushing a commit that changes `.github/workflows/*` probably needs the `workflow` scope. **Every one of those GitHub-side statements is marked "confirm against GitHub's current documentation" in the source, and none has been exercised against real GitHub** (see "Unverified").

**Gold validation runs through the real pipeline, not a standalone script.** `--agent gold` writes the instance's `gold_files` into the checkout (each through `confine`, all checked before any is written) and calls `verify_attempt(1)` as an agent would; `--agent gold` forces no PR, in the CLI and in `run_task` itself. A standalone validator would re-implement clone, export, overlay, verify and score and then drift from them. The runner is run twice (`gold-1`, `gold-2`, at $0 of LLM cost) and `repolace-eval gold --runs gold-1,gold-2` writes `eval/instances/VALIDATION.md`. An instance is accepted only if both runs scored `passed`; the attempt-0 baselines are identical across the runs (a suite whose baseline changes between two runs of one commit is flaky and makes every later score ambiguous); every fail-to-pass id was **collected** at baseline (an id in no result bucket and in no module that failed to import is almost always a node-id format mismatch between SWE-bench and our plugin, and as an agent run it would be charged to the agent), checked first; and every one was **red** at baseline (`expected_not_red`). It never edits an instance file; it *proposes* `targeted_p2p` (pass-to-pass over the fix's own test files) when the longest run reaches half the suite timeout, because every task runs the suite at baseline and again after each attempt, so a suite near its timeout turns into unscoreable runs; and also when that run, padded the same way, would make a task outlast the runner's per-task wall clock (see "The sweep"). **If the gold patch does not score PASSED the instance is dropped, not "fixed"**: that is what makes the number a measurement of the agent rather than of how well an instance was prepared. Gold validation is also the cheapest experiment that retires the install-masking risk above before any LLM spend.

**The sweep** (`enqueue`, `run`). `enqueue` writes `eval/runs/<run>/manifest.json` (the repolace commit, the model, the stage models, the limits, the instances, runs per instance, the agent) atomically **before** inserting the first row, then inserts the rows idempotently (`ON CONFLICT DO NOTHING` on `uq_tasks_eval_instance_run`), all-or-nothing on resolution (an instance whose repository the App has not synced is an error that says so). It refuses a modified tracked tree (`--allow-dirty-tree` to override), because a sha that does not describe the code that runs is worse than none. `run` starts up to K (`-k`, default 3) `python -m repolace_pipeline.cli <task_id> --agent {llm,gold} [--no-pr]` subprocesses, each in its own session so a hung task is killed as a group, logging to `eval/runs/<run>/<task>.log`. **K is a RAM decision** (each child loads the embedding model and starts a container with a 2 GB limit; the source estimates about 10 GB free for K=3). **A task row is never re-queued**: `task_test_runs` is unique on `(task_id, attempt)`, so a second run of one row would fail on insert at best and mix two runs' evidence at worst. Every status write by the runner is `RUNNING -> FAILED` and conditional on the row still being `RUNNING`; this covers a child killed on the wall-clock timeout, a child that died leaving its row `RUNNING`, and `--mark-abandoned` for rows whose runner died (stale `RUNNING` beyond the timeout plus a 600 s grace, marked `runner: abandoned`). The runner refuses to start if its `--agent`, `--model` or `--timeout-seconds` disagree with the manifest. **The wall clock's default (11,700 s) is derived, not chosen** (`enqueue.task_wall_clock_bound`): the index-lock wait (1,200 s) + the environment build (2,400 s) + the baseline suite (1,800 s) + the agent's wall budget (3,600 s, which contains every scored suite that starts inside it) + one scored suite that starts just before that budget runs out (1,800 s) + 900 s for the stages no constant bounds (clone, embedder load, the task's own index pass, review, push, PR). A shorter limit would kill legitimate slow-suite tasks as `runner: timeout`, which the report counts as harness errors, so they would leave the secondary `passed / admissible` figure; a test holds each term equal to where it is defined. An instance whose spec sets a longer suite timeout needs a longer `--timeout-seconds`; `gold` proposes `targeted_p2p` when the measured suite (padded as for the suite-timeout rule) would make a task outlast the runner (`--runner-timeout-seconds`, default the runner's). `--max-total-usd` is checked before each dispatch against `SUM(llm_calls.cost_usd)` for the run, so tasks already in flight finish and the total can exceed it by up to K times the per-task cap. The child's environment is an **allowlist** (the `REPOLACE_BENCH_GITHUB_TOKEN` name is excluded explicitly), plus `GATEWAY_STAGE_MODELS` when `--model` is given; SIGINT, SIGTERM and SIGHUP cancel the run and kill the children (an earlier version left SIGTERM children running and spending). Exit codes are the pipeline's: 1 only when repolace itself broke.

**The report's headline accounting is the claim** (`eval/harness/report.py`, written down once in its module docstring and repeated beside the number). **`passed / planned`**, where *planned* is the grid in the run's manifest (`instance_ids x range(runs_per_instance)`) and **every planned row that is not a pass is a non-pass, whatever the reason**: a failure, a `passed_with_test_edit` (never a pass, approved or not), a harness error, an inadmissible row. Excluding rows after seeing the results is what a sceptical reviewer calls cherry-picking, so the headline does not; `passed / admissible` is printed only as a labelled **secondary**, with the exclusions listed. The grid is checked against the database, not the reverse: a planned row that is missing or still queued/running **withholds** the headline unless `--allow-partial`, which marks it `PARTIAL (n of m)`; a run with no manifest has no grid and is marked `UNANCHORED`. Every finished row lands in one bucket by `classify`, first match wins: unfinished, harness error (status `failed` only), inadmissible (finished, outcome NULL), `passed_with_test_edit`, `passed`/`failed`. **A stop reason of `llm_error` is not a harness error**: it covers non-transient model errors too (a context-window overflow, an unparseable replayed call), which depend on how hard the instance is, and the scorer already gives such a task an outcome, so it is counted by that outcome and shown in its own column. The interval is a percentile bootstrap **over instances** (the runs of one instance are not independent: an instance a model can fix, it mostly fixes every time, so an interval over pooled rows is far too narrow); the per-run range is the spread with the instances held fixed and is labelled as not an interval. **At N = 15 to 20 the 95% interval is about 30 to 40 percentage points wide**, and one instance moves the rate by 1/N. Marks printed on the figure: `UNCURATED` (a pass whose reason says no curated fail-to-pass list was used), `UNANCHORED`, `PARTIAL`, `NO-LLM-CALL PASSES` (a pass that made no model call is a gold or stub run filed under the wrong id), and `UNEQUAL RUNS PER INSTANCE`. A run that mixes models **withholds** its headline (a rate over two models is a statement about neither). Comparisons between models use only instances scored under both, on `run_index` 0, and print discordant counts and an **exact McNemar p-value** and no difference of rates: 8:0 gives p = 0.008, 7:1 gives 0.07, 6:2 gives 0.29, so at 20 instances a 20 to 30 point gap between two one-run models is not distinguishable from noise. A p95 is printed only from 40 points up. Cost and latency are **censored** by the $2 cap and the wall-clock limit (a task stopped by either shows the limit, not its cost to finish), and latency is claim-to-completion with the sweep's parallel contention in it. `--predictions` exports SWE-bench-format predictions for a cross-check with the official harness, which uses different pass criteria (node-id format, pass-to-pass scope, collection-error handling), so exact agreement is not expected.

**Contamination and honesty disclosures, which must travel with any number.** The instances are a filtered subset of a public benchmark that models have **probably seen**, so the number is **not the published Verified score** and does not predict performance on unseen issues. The prompt omits the issue number, URL and `instance_id`, but **the issue text itself can carry upstream identifiers** (a repository name in a traceback path, a linked issue), and a model that recalls the upstream fix from training is indistinguishable, in the pass rate, from one that derived it. Controls recommended and **not implemented**: a second set of issues filed after the models' training cutoffs, reported separately; the similarity of the agent's diff to the gold patch; an "edits before exploring" signature in the trajectory (a model that edits without reading is probably recalling); and no outcome-bearing text pushed to the bench repository (already held for commit messages, and a benchmark PR body carries counts, never test ids). The report prints the contamination, subset and small-N caveats beside the headline; the subset caveat lists the five ways the subset differs from Verified (allowlist, simple-fix filter, round-robin cap, gold-validation pruning, the seed).

**The retrieval eval** (`repolace-eval retrieval`, `eval/harness/retrieval_eval.py`) is planned before it spends: `--plan` counts chunks and prints the bill, and a real run refuses if `repos x strategies` exceeds `--max-index-equivalents` (default 35) and skips, loudly, any repository whose first index exceeds `--max-chunks-per-repo`. **A repository is skipped whole, never trimmed**: a smaller corpus than production searches would make every recall number look better than it is. Eval rows are made invisible to the product (a synthetic installation id -1, negative `github_repo_id`, `is_active=False`); a test pins that the API's sync never touches them. The metrics credit the *innermost* overlapping chunk, a query with no old-side gold (a patch that only adds files) is skipped and counted rather than scored as a miss, and the switch rule is in "Open questions" under embedding truncation.

## Task bookkeeping (migrations 0012 and 0013)

- **0012:** `llm_calls`, `tasks.issue_body`, and the nullable benchmark columns `tasks.eval_run_id`, `instance_id`, `run_index`. **`llm_calls` lives in Postgres** for the reason `task_test_runs` stores raw sets: cost, latency and the trajectory *are* the benchmark's evidence, and none can be recovered once the call is over (a cost not captured then cannot be re-priced later without re-running, and a trajectory cannot be inspected once the clone it came from is gone). Benchmark rows are queryable from `tasks` itself rather than from a second store that could drift. The price is that the table holds repository source verbatim, which matters for private repositories (redaction strips credential-shaped strings and the exact keys the gateway holds, not code). `llm_calls.cost_usd` has eight decimals where `tasks.cost_usd` has four, because a cheap-model call prices in thousandths of a cent.
- **0013:** `tasks.patch_diff`, `tasks.score_reason`, `tasks.agent_stop_reason` (a string behind `ck_tasks_agent_stop_reason` with the eight values, not a Postgres enum, so adding one is a drop-and-recreate of one constraint instead of an `ALTER TYPE`), `registered_repos.index_strategy`, the all-or-none CHECK `ck_tasks_eval_columns_together` (`eval_run_id`, `instance_id` and `run_index` are all NULL or all set: the unique index below ignores rows with a NULL, so without it an enqueue that forgot `run_index` would silently lose its idempotency), and the partial unique index `uq_tasks_eval_instance_run` on `(eval_run_id, instance_id, run_index) WHERE eval_run_id IS NOT NULL`, which makes `enqueue` idempotent.
- **`patch_sha` stays a git sha** (the squashed commit when a PR was opened, else the scored commit at HEAD) and **the diff itself is in `patch_diff`**: a benchmark task that does not pass never pushes, so its commits die with the clone and the sha would point at nothing. `patch_diff` is NULL for a task that never reached the agent and `''` for one that did and changed nothing.
- **`score_reason`** is `Score.reason`, which `score()` computed and the pipeline used to discard; the report needs the sentence, and rescoring later is lossy (the `baseline_files` set that spares `django/test/client.py` is not stored).
- **`cost_usd` is NULL, not 0, when no priced call was made** (the stub and gold runners, a task that failed before the agent, calls that exist but none priced): "free" and "never priced" are different claims, and zeros would drag the benchmark's cost mean down for every gold and stub row. It equals the sum of the task's `llm_calls.cost_usd`.
- **`error_message` has exactly one meaning: `failed` = repolace itself broke.** An agent-caused stop (budget, step cap, no change, an LLM error, giving up) is `completed`, with the scorer's outcome and `agent_stop_reason` set, and `error_message` NULL. The reason is accounting: the report counts a `failed` task as a harness error, which the headline (`passed / planned`) still counts as a non-pass but the secondary `passed / admissible` figure *removes from its denominator*, so an agent-caused stop that raised `StageFailed` would quietly *improve* the secondary number and blur which failures were the agent's. A task with no scored attempt scores `failed` (not inadmissible: that word is for an instrument that failed, and this one worked).
- **The terminal write is conditional on `running`** (`finalize.write_terminal`, one function that takes every column as a required keyword, so a path cannot forget one): a late or duplicate writer finds the row already terminal and changes nothing instead of resurrecting a finished task, which is what Phase 2's at-least-once delivery needs. NUL is replaced before the write, because Postgres cannot store it and a failed write after the push and the PR would leave the row `running` with a pull request open; a minimal fallback `UPDATE` exists for a payload the database still refuses.
- **The task row is also checked against the scorer:** `_check_against_scorer` fails the task if the agent's reported attempts or last attempt disagree with what the scorer recorded, because a graph bug that dropped `last_attempt` would otherwise complete as FAILED "no scored attempt" inside the denominator with attempt rows sitting in the database.

## Concurrency (decided)

Checkouts are per task, so two concurrent tasks on one repository are isolated on the filesystem for free; the shared state is the `code_chunks` rows. **The indexing-lock question is resolved with a bounded wait inside the pipeline, not with the runner's scheduling.** `reindex_if_stale` takes a *try*-lock (`pg_try_advisory_xact_lock`), so a second task on one repository is refused at once with `RepoIndexInProgress`, and that is the *normal* case for a benchmark (three runs of one instance). `_index` in `run.py` retries in 10 s steps up to a 20 min cap and then fails the stage with a message saying so; when the wait ends the index is normally current, so the task's own pass finds nothing to do. **A session must not be reused across `reindex_if_stale` calls:** the function owns its transaction (it commits, and rolls back on failure, because the lock is transaction-scoped), and `rollback()` expires every loaded ORM instance, so touching an attribute afterwards raises `MissingGreenlet` outside the greenlet; `_index` opens a fresh session per attempt. **Product limit, recorded, not fixed:** the index is per repository, not per commit (`registered_repos.indexed_commit_sha` is a single value), so two concurrent tasks on *different branches of one repository* see each other's index, which at best costs reindexing and at worst retrieves chunks from the other branch. Benchmark repositories have one branch (`main`), which is why it does not bite there.

## Deployment requirements for the sandbox host

- **Rootless Docker with cgroup v2 delegation of `cpu`, `memory` and `pids`** (see "Rootless is a deployment precondition" above); without it the resource caps are silently ignored.
- **The workspace's parent directory must be on a size- and inode-limited filesystem.** A probe or script can write as much as it likes into its own export, a bind mount that no container limit covers, and `discard` can leave behind files owned by the sandbox's subuid that the host cannot delete. `task_workspace` takes a `parent_dir`, but **`run_task` and the CLI do not pass one**, so in practice the temp directories are created under the process's `TMPDIR`: put the quota there.
- **`prlimit` (util-linux) on the host.** The `grep` tool runs git under it, and `build_toolbox` calls `require_prlimit()` so a missing binary fails when the toolbox is built, not on the first search a model makes.
- **Expect an image rebuild the first time a run follows an upgrade.** The plugin's bytes are part of the image cache key (it is `COPY`ed in), and the plugin changed when the per-run nonce was added.
- **A priced model and a provider key.** `claude-sonnet-5-5` needs its `[price]` table in `gateway/models.toml`, and `ANTHROPIC_API_KEY` must be in `.env` (the key is handed to LiteLLM per call and is never exported into `os.environ`).

## Operations

- `uv sync --all-packages` (plain `uv sync` prunes workspace members).
- **Test database isolation:** `db_session` TRUNCATEs every table before every test, so two test runs that share a database corrupt each other with failures that look like real bugs. Parallel checkouts each set `REPOLACE_TEST_DB_SUFFIX` (an underscore, then 1-32 of `a-z`, `0-9`, `_`; default `_test`; an empty value is refused). `REPOLACE_TEST_DB_REQUIRED=1` and `REPOLACE_TEST_DOCKER_REQUIRED=1` turn a missing Postgres or daemon from a skip into a failure.
- **Test file basenames must be unique across the whole repository** (there are no `__init__.py` files, so pytest's prepend import mode resolves `test_config.py` to whichever directory was collected first, and a duplicate fails only in a whole-suite run). Prefix new files with their area; check with `find . -name 'test_*.py' -not -path './.venv/*' -not -path './*/.venv/*' | xargs -n1 basename | sort | uniq -d`, which must print nothing. The same holds for `*_support.py` helpers.
- **Run `alembic check` after touching models.** It is what caught the missing GIN and HNSW index declarations.
- No `alembic upgrade` against the development database from a test run: the `-m db` fixtures migrate their own `<db>_test<suffix>` database.

## Phase 1 status

**On `main`:** the sandbox and scoring extensions, the nine tools, retrieval strategy plumbing and `build_query`, the agent graph with its feedback filter, the pipeline seams, gate, PR text and finalize, the benchmark harness, and the integration that wires the real agent into `repolace-run-task`. **Not yet measured:** any benchmark number, any retrieval number, the cost per task, the suite wall times, whether the curated fail-to-pass ids match what our plugin reports, and any real run against a provider or Docker. **What produces the number:** price the headline model, gold validation, a dry run, the sweep, then `repolace-eval report`.

**How the real agent is wired (merged; verified by reading the code and by the integration stream's `-m db` tests, not by a real run):**

1. `pipeline/repolace_pipeline/agent_runner.py::LLMAgent` calls `run_agent` (never `run_graph`, so every run draws a fresh nonce) with the `AgentDeps` the pipeline builds, inside the gateway `task_scope` and `TaskBudget` the agent stage opens; the budget clock starts at the agent stage, not before the clone, index and baseline.
2. `cli.py` builds one gateway client per process and checks the agent stage's model (and fallback) **before any task row is claimed**: a model with no price is exit code 2 naming `gateway/models.toml`. Provider keys must be in `.env` (the runner's environment allowlist does not pass them to children). `GATEWAY_STAGE_MODELS` is honoured through the gateway's own loader.
3. **The CLI default is `--agent llm`**; `stub` and `gold` remain, `gold` forces no PR. Exit codes: 1 only when `error_message` is set; 2 usage, not found or unpriced model; 3 not claimable.
4. Retrieval uses `build_query(issue_title, issue_body)`: the semantic arm gets `query.semantic`, the keyword arm `query.keyword`, and the strategy is the repo's stored `index_strategy` (else `truncate`). A title made only of control characters falls back to `issue <N>` rather than failing retrieval.
5. Benchmark mode passes `expected_fail_to_pass` from the loaded instance into `score(...)`, so a PASSED reason no longer ends "uncurated".
6. **`GraphRecursionError` is a harness error (FAILED), decided.** The graph's shape (at most 7 steps against a limit of `4 * max_attempts + 8`) cannot reach that limit by itself and nothing in an issue or repository can cause it, so only a routing bug in repolace can. Counting it as a step cap would hide the bug inside the headline denominator, and a run that had already scored a passing attempt could even open a PR. `_agent_stop_from` maps only `BudgetExceeded` and `LLMCallError`.
7. **Known limits recorded by the integration security review (not fixed):** an authentication or billing failure from the provider is scored as an agent failure (`llm_error`, visible as its own column in the report) because the gateway's `LLMCallError` carries no kind; any non-protected file is writable, including files CI executes (`Makefile`, `noxfile.py`), so a pushed agent branch can carry an edited build file: with `llm` now the default, run the first smoke test on a toy repository with GitHub Actions disabled; the CLI preflight reads the gateway's private `_verify_usable` and `_config` (a public `LLMClient.preflight` is wanted); the retrieval index is per repository, not per commit, so concurrent product-mode tasks on one repository can see each other's index.

## Open questions / not yet decided

- ~~Exact "task completed successfully" definition~~ — **decided, see "Task success criteria" below.**
- Issue-list filtering rule (label-based, e.g. only `bug`/`good-first-issue`) so users aren't picking from unfiltered noise
- ~~Single-flight vs. concurrent tasks per repo~~ — **resolved: concurrent, see "Concurrency" below.** Checkouts are per task, and the shared index is protected by the advisory lock plus a bounded wait. What stays open is a product limit, recorded there.
- **Embedding truncation — the most serious known limit on retrieval quality.** The chosen model's `max_seq_length` is **128 tokens**, which is very small for code. Measured by real tokenization over this repo's own 238 chunks: **99 (41.6%) exceed the budget** and are silently truncated, embedded from their opening tokens alone. Median chunk is 105 tokens — the *typical* chunk sits just under the ceiling, so the corpus is crowded against it. By type: functions 52.7% over (median 131, already past the limit), module 46.9%, class_skeleton 33.3%, method 30.4%. The longest chunk is 1328 tokens, 10.4x the budget; `CodeChunk`'s own skeleton is 771 tokens, of which the encoder sees 128 — **83.4% never reaches it**, cancelling most of the benefit of enriching class skeletons.   **This is set up as a benchmark variable, not a guess.** `rag/retrieval/strategies.py` implements four interchangeable strategies (`truncate`, `head_tail`, `windows`, `signature_docstring`), selected via `embed_texts(..., strategy=...)`. **The strategy is now threaded through indexing and search** (an earlier revision of this note said the harness "should" run the grid because it was not): `reindex_if_stale`/`index_repo` take `strategy`, `hybrid_search` takes `query_strategy`, and `PipelineSettings.embedding_strategy` (default `truncate`, so changing nothing changes nothing) is what the pipeline passes to both. **`registered_repos.index_strategy` records what an index was built with** (NULL means the legacy `truncate`), because without it a repo whose commit is current would never reindex after a strategy change and old and new embeddings would mix in one index. A mismatch therefore forces a **full** reindex, not an incremental one; the field's own comment warns that a different `embedding_strategy` forces that on every repo it meets, which is why the default must stay `truncate` until the eval picks a winner. `repolace-eval retrieval` runs the grid (4 index strategies x 2 query strategies, `truncate`/`head_tail`) against gold-patch hunks with no LLM call, and **the switch rule was stated before any number exists**: a cell replaces `truncate`/`truncate` only if its paired chunk-MRR gain is at least `--min-gain-pp` (default 10 percentage points) **and** the 95% bootstrap interval over instances excludes zero. It is one of eight cells compared on the same few instances the agent is benchmarked on, so a winner is exploratory. The chunk metrics credit only the *innermost* chunk overlapping a gold hunk: a class skeleton's span is the whole class and the module chunk's span runs from its first to its last top-level statement, so crediting any overlap would score a hit when only a chunk whose content does not contain the changed line was retrieved, inflating chunk recall in a strategy-dependent way. No retrieval number has been measured yet. Measured over this repo (238 chunks, limit 128) — "still truncated" is the share of embedded texts still over budget, "encoder tokens" is tokens fed to the encoder as a share of original content, which exceeds 100% for `windows` because overlap feeds some tokens twice:

  | strategy | passes/chunk | still truncated | encoder tokens | trades away |
  |---|---|---|---|---|
  | `truncate` (current) | 1.00 | 41.6% | 54.4% | everything past the head |
  | `head_tail` | 1.00 | 0% | 54.4% | the middle of the body |
  | `windows` | 2.05 | 0% | 120.4% | 2x indexing cost; risks blurring long chunks toward the centroid |
  | `signature_docstring` | 1.00 | 0% | 32.4% | the body entirely — weakest on undocumented code, where bugs live |

  The orthogonal axis is the model itself: a 512-token context would cover the large majority of chunks outright and can be combined with any strategy. Evaluate it as a second variable in the grid rather than a fifth strategy.

  Note the figure of "26%" previously recorded here was **wrong**. It came from a `len(text) > 4 * max_seq_length` character estimate; code tokenizes far denser than 4 chars/token (closer to 2.5 here), so everything between ~320 and 512 characters was miscounted as fitting. `embed.py` now tokenizes to count instead of estimating.
