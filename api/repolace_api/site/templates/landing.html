How a task runs

  1. 1

    Pick an issue

    Choose an open issue and the branch the fix should target.

  2. 2

    Retrieve

    The repository is indexed by function and class so the agent reads the code that matters, not the whole tree.

  3. 3

    Plan and edit

    The agent writes a change and revises it when your tests disagree, within a fixed step and spend budget.

  4. 4

    Verify

    Your suite runs in a rootless container, once on the base commit and once after the edit, so a pass means something went from red to green.

  5. 5

    Open the PR

    On success a pull request opens against your branch with the diff and the test results.

Built so you can say no

  1. Your tests are the judge

    A task counts as fixed only when failing tests turn green and nothing that passed before breaks. Edits to test files are flagged, not hidden.

  2. Generated code never runs on the host

    Verification runs in a rootless container with resource limits, against a copy of the source with no .git inside.

  3. A hard spend cap per task

    Every task has a fixed model budget, a call limit and a time limit. A runaway task stops; it does not bill you for hours.

  4. You decide what merges

    repolace opens a pull request. Reviews, required checks and merging are GitHub's, exactly as for a human contributor.
